# Connected apps

Choose a listed app from the searchable **Your apps** directory to connect without looking up an address. Notion, Todoist, Linear and Sentry use documented official endpoints. Search works locally; sign-in and explicit tool review are still required. Custom links and local programs remain available through **Add an app**. See [APP_DIRECTORY.md](APP_DIRECTORY.md) for protocol checks and live-account limits.

Open **More → Connect apps** from the chat’s bottom bar. **Your apps** is a separate page; visiting it never adds a chat message. Choose **Add an app**, paste its Streamable HTTP MCP address, and press **Continue**. Relay checks its available actions, documents and templates without running an action or retrieving their contents. Apps that need no authentication go straight to permission review. An authentication rejection offers **Sign in with browser**; a token can be entered under **Other connection options**. Network failures remain inline errors that you can correct and retry, rather than guessed sign-in flows. Checking an address never opens a browser window or saves a connection.

The app name is filled from the address (or “Local app” for loopback), and is editable during tool review without repeating discovery or sign-in. Choose **Connect app** to save. Tools still default to **Ask each time**. Credentials and manual OAuth client registration remain collapsed. Existing Google Mail and Calendar settings remain available from this page.

## Programs in Relay’s computer

In **Add an app → Other connection options**, choose **Use a program in Relay’s computer**. Enter its program and one argument per line, then **Run and find tools**. Folder and masked environment values stay under a disclosure. The program must already be installed in the running computer, with control given to Relay. Starting a program can change workspace files even during discovery; the form explains this before launch. A slow check can be cancelled without saving the app. Leaving the page also cancels unfinished discovery.

After discovery, the same permission review, app name, assistant scope, @ selection, pause/disconnect controls and exact action reviews apply. Environment values are encrypted with saved app credentials; owner responses show only their names. Blank saved placeholders retain the existing values for the same program/arguments/folder. Changing any of those requires entering saved values again. Removing a variable removes it from the next saved configuration. Put credentials in environment values, not command arguments.

Each session runs in a fresh bounded container using the computer’s pinned image and workspace volume. It has no host mounts, inherited Relay credentials, direct internet, published port, privileged user, or persistent Docker logs. Its program reads/writes normal newline-delimited MCP over stdin/stdout. Session cleanup stops the whole process namespace, including detached descendants. Takeover, stop, shutdown and restore-point work stop local sessions before continuing. After a server crash, startup reconciles the durable session journal; the guest also has a 90-second lifetime bound. An uncertain action retains its receipt and is not replayed automatically.

Local programs support action calls, document reads and owner-chosen prompt templates. Programs requiring outbound internet, software installation, persistent in-memory sessions, sampling or interactive MCP Apps need further support. Use an HTTP app connection for a hosted service. See [local tool implementation and verification](LOCAL_TOOLS.md).

## Choose an app while writing

Type `@` in a message, or tap the **@** button beside Attach files when eligible apps are connected. Pick an app by keyboard or touch. A small removable chip stays with the draft; choosing from the button does not change the text. The picker also handles group participants, with distinct labels for people/roles and apps. An email address does not open the picker. A mention inserted at the cursor preserves the rest of the sentence.

Only enabled connected MCP apps with usable actions or content and access for every eligible recipient appear. After choosing a specific group recipient, apps available to that role become eligible. Up to eight apps can be selected. Selections persist per conversation through navigation and reload, including separate reply-thread drafts. A changed or unavailable app remains visible as **Choose again**, so it cannot silently disappear and broaden the request. Send rejects stale selections and preserves the draft. **Connect apps** in the picker opens the existing separate page and does not add messages.

Sending stores server-resolved app names, IDs and connection revisions on the message and request. For that request, `list_app_tools` and `use_app_tool` are limited to those selected app revisions. Questions, reviewed-action continuation, specialist handoffs, computer website waits and background jobs carry that frozen selection; the next draft cannot change it. Current role/tool permissions still apply. Selecting an app grants no new access and does not approve an action. This selection scopes connected MCP apps, not built-in workspace/computer/Google tools. Messages with no app selection retain normal app discovery. Plain text such as “@Notebook” without choosing a result is ordinary text, not a stored selection.

Tools start at **Ask each time**. An inline review shows the exact fields the app will receive, with the destination, tool name and raw JSON under **Action details**. Approve runs that exact action; Decline runs nothing. After a confirmed successful result, Relay resumes the original request once, using its saved assistant, model connection and question context. Completed reviews become compact receipts. Errors and uncertain outcomes stay visible and do not silently trigger another write.

**Allow reads** is available only for tools whose server reports a read-only annotation, and only after the owner selects it. This annotation is a claim by the connected app, not an isolation boundary: use a trusted server. **Off** removes a tool from the assistant’s available tools. **Who can use this app?** can restrict a connection to Main or selected assistants. Pause, change permissions, refresh or disconnect on the same page. Connection changes invalidate waiting reviews and cancel local in-flight requests; cancelling a request cannot undo an action already received by the remote app.

## Transport and data

Relay uses the official MCP TypeScript SDK for Streamable HTTP, including JSON and SSE responses, session/protocol headers and paginated action/document/template discovery. Application policy, persistence, reviews and UI are independently implemented. There is no competitor application code or artwork in this feature.

Use HTTPS, or HTTP on the Relay server’s loopback interface. Localhost means the computer running Relay, including when using a phone. Redirects are rejected. Each operation creates a fresh session, rechecks the current tool definition before dispatch and attempts a bounded session termination. Calls have a 45-second timeout and bounded request/response sizes. Up to 20 apps and 100 tools per app are supported. Arguments are checked against object input schemas (draft-07 or explicitly declared 2020-12, without remote reference fetching or format validation).

The assistant first lists app/tool descriptions, then requests a specific tool’s schema and uses its connection revision. The app receives tool arguments and standard protocol/session messages. Text, structured results, embedded text resources and image results can enter the selected model’s context. Binary resources, image and audio results become saved files; a PNG, JPEG or WebP first result can also enter model image context. Resource links are returned as data and are never fetched automatically. Other content types are reported as unsupported. App descriptions and returned content are untrusted source material, never new owner instructions or permissions.

Bearer tokens are encrypted with AES-256-GCM in the private SQLite secrets table using `model-vault.key`. Back up the database and key together with Relay stopped. The key and database are on the same server; this is not protection against a compromised server account. Tokens are absent from public workspace state, exports, SSE and model requests. Raw error bodies are not exposed. Exact echoes of the configured token are redacted from app results. Owner authentication and same-origin checks protect connection management. The browser-only OAuth entry and callback instead require a short-lived one-use ticket followed by matching state and a browser-bound HttpOnly nonce cookie; these routes never expose workspace content.

Before an outbound tool call, Relay records a durable operation receipt. A completed operation returns its stored result on recovery; an interrupted or ambiguous operation is never dispatched again under the same receipt. There is no general way to guarantee whether a remote app completed a write after a network failure. Check that app before preparing a new action.

## Browser sign-in

Relay supports authorization-code OAuth with PKCE S256, protected-resource metadata, authorization-server discovery, resource-bound tokens and dynamic client registration. A pre-registered client ID and optional secret can be entered under **Other connection options → Registered OAuth client**. Register the callback as `https://YOUR-RELAY-SERVER/api/connectors/oauth/callback`, matching `RELAY_PUBLIC_URL`. A later sign-in reuses the encrypted registered client only when both the app endpoint and authorization issuer still match. Use a stable public HTTPS Relay address when connecting from another device. Local loopback HTTP is supported for development.

Providers must publish protected-resource metadata at a standard well-known location, identify the exact configured MCP resource, expose discoverable authorization-server metadata with a matching issuer, and advertise S256. Dynamic registration or a manually registered client is required. Metadata/token requests reject redirects, pin public DNS results, block private addresses, use standard public HTTPS ports and bound response sizes. Local development authorization endpoints must use the same explicitly configured loopback origin as the MCP server. Custom challenge-only metadata locations, client-ID metadata documents, incremental scope challenges and vendor-specific authorization extensions are not covered yet.

Access tokens, refresh tokens, client secrets, pending state and PKCE verifiers are encrypted in the private SQLite secrets table. Sign-in expires after ten minutes. A one-use entry link opens the provider in a browser; its callback is bound to that browser. Desktop and iOS open the system browser through a restricted native bridge. The phone does not need to copy the Relay owner's session into Safari. Reloading Relay can recover the pending sign-in in the same tab/WebView; a completed login still waits for explicit permission review and **Connect selected tools** (or **Connect app** when content is available).

Before a tool call, an expiring token refreshes once, shared by concurrent requests. Refresh preserves tool policy revisions. Relay records the refresh attempt before sending it: a crash or lost response requires a new sign-in rather than blindly replaying a rotating refresh token. A provider rejection before tool dispatch also marks the app for sign-in. Tool actions themselves are never retried automatically. Removing/changing a connection during refresh cannot restore its old authorization or dispatch the waiting tool. Disconnect removes Relay’s saved credentials and pending sign-ins; remove the provider’s consent separately if you also want to revoke its grant.

App documents and prompt templates share these controls, including content-only connections and an inline **Use template** choice. See [APP_CONTENT.md](APP_CONTENT.md) for protocols, bounds and verification.

## Verification and limits

`npm run apps:mentions:test:ui` exercises keyboard/touch selection, cursor edits, email boundaries, role filtering, stale revisions, draft/reload persistence, and a real controlled HTTP model → MCP read → exact reviewed write → frozen continuation. `npm run apps:mentions:test:mac` uses the packaged Mac client. `npm run apps:mentions:test:ios` uses native iPhone WebKit and a disposable HTTPS fixture. See VERIFICATION.md for completed runs and platform qualifications.

`npm run apps:test:ui` covers address-only and token setup, inline failure recovery, automatic names and renaming during review, then exercises the actual connection page, HTTP APIs, worker, agent tool loop and independent HTTP MCP server on desktop and phone layouts. It discovers tools without executing them, grants reads, prepares a write, reloads the review, approves it, verifies one external write and one continuation, preserves drafts and checks navigation, accessibility and overflow. `RELAY_CONNECTORS_NATIVE=true npm run apps:test:ui` runs that flow in the packaged Mac application.

`npm run apps:signin:test:ui` covers browser sign-in, cancellation/retry, a page reload while signing in, temporary loss of polling, explicit tool permissions, a real MCP read, owner/cross-origin route protection, draft/history preservation and accessibility on desktop and phone layouts. `RELAY_CONNECTORS_NATIVE=true npm run apps:signin:test:ui` uses the packaged Mac app and its real IPC URL validation; OS browser launch is captured into a separate Chrome session. `npm run apps:signin:test:ios` exercises the native WebKit → Safari → native permission-review round trip using an isolated HTTPS test server and a disposable Simulator.

`tests/connectors.test.mjs` and `tests/connector-oauth.test.mjs` cover JSON/SSE, schemas, credential isolation, endpoint restrictions, reviews, cancellation, role/revision restrictions, durable recovery, frozen continuation, PKCE/state/browser binding, encrypted persistence, serialized token rotation, provider revocation, lost refresh responses, restart recovery and native opener validation. These use independent controlled HTTP providers, not a connected third-party account or a hosted-model judgment test.

The legacy HTTP+SSE transport, marketplace installation, remote sampling/elicitation, resource subscriptions and every vendor’s MCP extensions remain unimplemented. Hosted account acceptance, real-model task quality, physical devices, Android native runtime and distribution signing remain separate gates. See [product parity](PRODUCT_PARITY.md).
