# Trusted browser runtime (experimental)

Status: the production opt-in browser now runs in its own restricted Linux container, separate from the agent command runtime and shared desktop. Its existing owner API, Computer-page interface and assistant tools remain **off by default**. The tests below distinguish earlier host-Chromium protocol fixtures from current real-container evidence. Physical devices, Android and live accounts remain unverified. The ordinary desktop browser still has the shared-profile limitation described in [COMPUTER.md](COMPUTER.md).

This is original implementation code. The product comparison informed the requirements; no competitor code or assets were incorporated.

## Current browser process boundary — October 13, 2026

The production server supplies `BrowserContainer`; it never falls back to host Chromium if the container fails. It uses the existing prepared Relay desktop image by immutable digest, with a fresh random container identity. It has no workspace, X display, host directory or Docker-socket mount; no published port; independent PID, mount and network namespaces; a read-only root; and only a 256 MiB temporary filesystem for its disposable profile. It runs as UID/GID 1000 with all capabilities dropped and no-new-privileges, bounded to 1 GiB memory with no extra swap, two CPUs, 128 processes and 128 MiB shared memory. Unexpected image-declared volumes/build hooks are refused. The actual created settings are checked before and after attachment.

Chromium runs headlessly inside that container with `--network none`. CDP uses inherited pipes through a narrow local Node/Docker adapter; no debugging TCP port or host WebSocket proxy is created. Browser requests still pass through the separate server broker for public-address validation, TLS, exact request reviews and bounded page-resource permissions. The container has no direct TCP/UDP route, including if browser-level proxy settings are bypassed. Persistent cookie surrogates and storage are restored from the existing encrypted server vault; the container profile is discarded. Chromium’s nested sandbox is disabled inside this non-root restricted container because the standard Docker policy does not provide its required namespace setup. This is a container boundary, not proof against arbitrary Chromium, kernel or Docker escapes.

The adapter removes its owned container and temporary helper when the browser exits or its server-side pipe closes, including after parent SIGKILL. A lost create acknowledgement is recovered only by checking that launch’s random name, owner, immutable image, command and full isolation settings. A disconnected browser invalidates in-flight observations and action state; the next explicit action can open a fresh container. No action is automatically replayed. A stopped/unreachable daemon can delay cleanup; no host browser is substituted. Existing Docker/Colima and a prepared image are required; only local Unix-socket engines are accepted in this first implementation. The owner’s normal Docker context is not changed.

The interface stays the same: one Browser view, owner takeover/sign-in, and inline review. This does not introduce another setup dialog or add history messages. The ordinary shared desktop remains independent. Host-Chromium construction without a supplied runtime remains available to independent protocol fixtures; it is not reachable as a fallback from the production server.

Primary references: Docker’s [none network driver](https://docs.docker.com/engine/network/drivers/none/) and [resource controls](https://docs.docker.com/engine/containers/resource_constraints/), plus Playwright’s [custom launch API](https://playwright.dev/docs/api/class-browsertype#browser-type-launch-option-ignore-default-args). The pipe bridges and policy validation are original Relay code. See the latest VERIFICATION.md entry and `browser-container-*.json` evidence for completed checks and limitations.

## Research and intended interaction

[Muse's security design](https://research.meta.ai/blog/security-and-safety-for-ai-agents-our-approach-with-muse), published September 8, 2026 and checked October 11, describes an external browser broker, private credential storage, credential surrogates, a restricted accessibility interface, a pause during human takeover, request inspection and taint tracking. Those are distinct requirements; encrypting cookies alone does not implement that architecture.

[Grok's computer documentation](https://docs.x.ai/grok-bot/computer-and-apps), updated October 8 and checked October 11, describes persistent shared browser sessions and owner takeover for sign-in and other sensitive steps. Relay needs both persistence and a separate credential boundary; shared sessions alone do not establish that boundary.

The intended product flow stays on the separate Computer page. Sign-in and takeover should require few actions, and consequential decisions should appear in the existing review area. Opening a page must not create chat messages. The opt-in interface keeps all waiting requests in one inline review area, with readable form values and expandable technical details. A main-document review now offers one bounded page-load decision for its same-origin rendering resources, with Only this request available for exact-only review. Other requests retain exact authorization. There are no per-request dialogs or ongoing origin grants. This is an explicit permission scope, not Muse’s learned risk classification or a general safe-read policy.

## Implemented authority

`server/browser-vault.mjs` keeps cookie values, saved login records and browser storage encrypted with the existing AES-256-GCM helper, outside workspace snapshots and exports. It requires HTTPS origins without URL credentials. A browser receives random cookie surrogates while the broker substitutes the real value only for the exact issuing origin. Cookie attributes are preserved for Chromium's normal scope, expiry and HttpOnly handling. Binary upload bytes are preserved during substitution; URL/form replacements are encoded. A revoked vault or changed login invalidates already-prepared requests, including a request waiting for its final DNS answer. A late response cannot restore cookies after revocation.

`server/browser-requests.mjs` freezes and encrypts the URL, method, headers and body before its first asynchronous operation. The review is bound to a digest of those exact bytes. Agent requests require an exact boolean decision unless covered by the owner’s bounded page-load permission described below. GET requests can have side effects; resource classification alone is never a claim of safety. Owner requests use the same transport but do not ask the owner to approve their own action again. The caller must supply a synchronous control guard returning true/undefined or throwing/returning false. The actor and guard are trusted server inputs, never model-supplied permission claims.

The transport validates the public destination again immediately before dispatch, pins the checked IPv4 address, verifies TLS, strips caller-controlled transport headers and does not follow redirects or retry. The final synchronous control/vault check and durable send claim occur after DNS and before socket creation. Concurrent approvals cannot dispatch twice. A restart, cancellation after dispatch or lost response requires inspection; it never triggers automatic replay. Initial DNS validation and total network dispatch each have a 20-second deadline, including a continuously streaming response. Response and upload limits are 8 MB each; at most 30 requests can be preparing DNS or live, including requests waiting for review. Completed history retains at most 40 records and 16 MB of encrypted payloads, prioritizing the just-completed request. Pending reviews remain visible ahead of history.

Request fingerprints now use a keyed digest, and the original masked review is preserved inside the encrypted receipt. Replacing or clearing a login cannot unmask the old review. The browser's explicit clear operation also removes request payload records, because login bodies can contain another encrypted copy of a credential. It retains input-free action identities so an old action cannot be replayed.

## Browser runtime and owner API

`server/trusted-browser.mjs` launches a separate headless Chromium process with its sandbox enabled, ephemeral contexts, and a deny-all fallback proxy. No CDP TCP port or shared desktop display/profile is configured. Service workers, WebSockets, OS-managed downloads and new popup pages are blocked. Approved HTTP file responses can now be saved by the broker into Relay Files as described below; Chromium never chooses a host download path. This implementation is separate from the Docker desktop and does not retrofit its shared browser with these protections. Full OS egress and resource-isolation auditing remains open.

Every intercepted request, including each redirect, passes through the request authority. Interception uses the [CDP Fetch request stage](https://chromedevtools.github.io/devtools-protocol/tot/Fetch/). Actual runtime testing found that the earlier Playwright routing harness did not cover redirected navigation reliably after attaching a CDP session: a redirect hit the deny-all proxy and sign-in failed. The runtime now has a separate acceptance check proving that each redirect hop waits for its own review. The earlier six-check harness remains a core contract test, not proof of production routing.

The narrow action interface supports opening HTTPS pages, clicking opaque accessibility targets, typing into supported editable fields, bounded keys and scrolling. It exposes [accessibility content](https://chromedevtools.github.io/devtools-protocol/tot/Accessibility/) rather than raw DOM or model-controlled scripts. Targets are bound to the page, actor, document generation and observed role/name/state; stale or renamed controls are rejected. Private fields have no model target or value, and known secrets are masked from observations. Owner screenshots remain on an owner-only path. These filters are not general secret redaction or taint tracking.

Actions have durable IDs and keyed input digests. Identical repeats return a receipt, changed repeats are rejected, and interrupted or uncertain work is not replayed. Private action payloads are removed when the action ends, while small identity records remain. A browser action has a five-minute ceiling. A changed computer-control epoch cancels requests, invalidates targets, closes the old page context and preserves encrypted cookies/storage. Closing that context prevents old page scripts from acquiring owner authority. It also discards unfinished DOM/form state; seamless handoff remains a product requirement. No page is automatically reopened after handoff.

Owner input in password/autocomplete credential fields is added to a bounded encrypted private-input registry before typing. The broker rejects known private values sent to another origin in literal, UTF-8, URL/form, common JSON escape or base64 representations. Arbitrary transformations, split values, unknown response tokens and hostile-script taint tracking remain unresolved. Do not describe this filter as a complete exfiltration defense.

`server/trusted-browser-routes.mjs` is registered after Relay's owner authentication, host validation and cross-origin write protection. HTTP action callers always have owner authority; a body field cannot impersonate the agent. Changing the page or clearing it requires actual owner control of the computer. Reviewing an agent request works without taking over and cancelling that request.

| Endpoint                                       | Purpose                                                                                                      |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `GET /api/private-browser`                     | Owner status and masked pending/recent request reviews                                                       |
| `GET /api/private-browser/view`                | Owner page preview, bounded field controls and masked requests; pending reviews do not wait for a screenshot |
| `POST /api/private-browser/actions/:id/cancel` | Stop the identified live action without replaying it                                                         |
| `GET /api/private-browser/screen`              | Owner-only screenshot                                                                                        |
| `GET /api/private-browser/accessibility`       | Owner observation, requiring owner control                                                                   |
| `POST /api/private-browser/actions`            | Begin `{operationId, action, ...}` and return its durable receipt                                            |
| `GET /api/private-browser/actions/:id`         | Poll an action without repeating it                                                                          |
| `POST /api/private-browser/requests/:id`       | Decide `{fingerprint, allow}` with an actual boolean                                                         |
| `POST /api/private-browser/clear`              | Clear browser contexts, credentials, storage and request payloads                                            |

For development only, `RELAY_TRUSTED_BROWSER_ENABLED=true` opts into these endpoints when `RELAY_DESKTOP_ENABLED=true`; The installed local Docker/Colima engine must have the prepared Relay desktop image. `RELAY_BROWSER_CHANNEL` applies to the separate public-reader/host test fixtures, not this production container. The default is false. There is no new user-facing switch or automatic change to existing installations. The host process is trusted and can read the vault. A compromised host/transport or browser escape is outside the verified boundary.

## Computer page and assistant tools

When the server opts in, Computer opens its Browser view; Desktop remains one adjacent button away. The owner can take control, enter a website, edit native fields over the page preview, submit a form, scroll, zoom, give control back and clear saved data. Fields and buttons come from bounded accessibility targets; they do not embed website HTML or execute website scripts in Relay's UI. Blur edits and the next button click share a queue, so a focused password is applied before Submit. Username fields display normal text to the owner while password fields stay concealed; both remain private to the model. Autocapitalization and autocorrection are disabled on page field editors. The control/handback bar stays visible when the phone keyboard scrolls the page. Targets remain stable across refreshes but still reject changed roles, labels, states or documents. The address updates after a redirect. Not every website control, iframe or login method is supported yet.

Request reviews show destinations and decoded form fields first; headers and raw data are under Request details. Large truncated or binary previews are identified. Allow & continue applies to the exact displayed fingerprints. A single eligible main-document review explicitly includes its bounded page-load scope; Only this request omits that scope. For forms and other reviews, newly arriving requests are not implicitly approved. Decline and Take control stop pending work. A pending navigation returns review status without waiting for its screenshot, avoiding a review/loading deadlock. Opening views, refreshing and managing sign-ins do not create chat messages.

The assistant receives `private_browser_look` and `private_browser_action` only when enabled. The server supplies an immutable action identity, ignoring any model-supplied identity. The tool waits on that receipt while the worker stays alive; the active reply offers a direct Open browser control. Cancellation aborts its browser context and pending requests. The existing global takeover pauses the assistant, and late observations cannot be delivered after an epoch change. Restart recovery can retrieve an interrupted browser receipt without replaying the click. A model's later decision to repeat an uncertain action is still subject to exact request review; these checks are not a general policy or taint classifier.

The desktop and 390px phone acceptance journeys use a real Relay server, SQLite worker, original independent HTTPS notebook and controlled HTTP model. They test sign-in, focus/blur ordering, a reviewed form submitted once, masked model observations, reload while waiting, decline, takeover with paused model dispatch, preserved Main draft/history, clear/cancel, light/dark accessibility and viewport fit. The authority is the production `PrivateComputer`; the fixture replaces its container inspect/pause/resume transport. It does not prove the actual Docker freezer, live provider/account behavior or full containment. The same journey additionally passes in the existing packaged Mac client connected to the current isolated test server; this verifies its remote-client path, not a rebuilt standalone Mac backend. The actual iPhone and container acceptance below uses the real Docker freezer. Android and physical-device acceptance remain open. The acceptance scripts never load the owner's workspace or browser profile.

## Downloads into Files

A reviewed main-frame HTTP response with `Content-Disposition: attachment`, or a clicked HTTPS link with an HTML `download` attribute, saves its completed bytes directly into Relay Files. The browser view shows the latest file and **All files**; the assistant's completed tool result includes the actual saved file IDs and returns file cards in chat. Owner downloads do not add messages. Previewing or downloading a saved result uses Relay's existing file controls, including the native export path where supported. This pass tests the browser/Mac renderer path, not native phone export.

Each agent request and redirect keeps its existing review. Page-resource permission does not grant a file-import scope. Only a current browser action may save a result; attachments outside that action, ordinary subresource responses, blob/data downloads, partial responses and unsupported content encodings are not imported. Per-action limits are four files and 8 MB combined, with the existing network/body deadlines. Bytes are saved after the broker's control check, and file metadata plus the action association commit in one SQLite transaction. Receipt replay returns the existing file IDs rather than issuing another network request. Deleted files are not recreated by replay. An interrupted action can still identify files that finished before the interruption.

UTF-8 disposition filenames are decoded, path components and control/bidirectional characters are removed, and no website filename becomes a filesystem path. Binary bytes are preserved. Filename, MIME and UTF-8 response content are checked against the vault's known-secret variants before entering the general Files library. This is not archive inspection, malware scanning, arbitrary-encoding detection or complete taint tracking. Files are shared workspace content; they may themselves contain private material. Clearing browser sign-ins does not delete intentionally saved Files.

An intercepted rejected download can keep the previous page visible, while its action reports failure. Requests rejected before their download response is known can still show a browser error page. No automatic retry occurs. A new action or takeover also wakes any already waiting preview poll, so a screenshot that started just before navigation cannot hold the review UI until its timeout.

Seven Node cases cover filename handling, byte/count limits, known-secret rejection, atomic rollback, deletion/replay and actual SQLite reopen. A further browser-agent test exercises the preview/action/takeover race. `npm run computer:test:downloads` verifies desktop and phone production UI with real Chromium and an independent HTTPS fixture: owner sign-in, CSV/binary output, redirects, no dispatch before review, no dispatch after decline, takeover during a response, metadata/file persistence, exact result cards, draft/history preservation and accessibility. `npm run computer:test:downloads-mac` repeats the flow in the existing packaged Mac remote client. Container pause/resume transport is stubbed in these tests; no live account, physical phone, signed distribution or complete security-boundary claim follows from them.

References: [Grok Bot files and results](https://docs.x.ai/grok-bot/files-and-results) and [Grok Bot computer](https://docs.x.ai/grok-bot/computer-and-apps), rechecked October 11, 2026. These inform the interaction; implementation is original.

## Bounded page loading

The October 11 follow-up reduces repeated reviews for a single page. When the only pending review is a main-frame HTTPS GET document, the interface explains that **Allow & continue** includes its same-origin images, styles, fonts, scripts and icons. **Only this request** keeps individual review. Forms, Fetch/XHR, child-frame documents, other origins (including another port), non-GET requests and body-bearing requests remain outside this grant. A document redirect always gets another review, even within the same origin. Same-origin resource redirects remain within the explicitly authorized scope; cross-origin resource redirects do not.

A permission covers at most **64 requests for 30 seconds**, ending earlier when its current action finishes, a new main document starts, control changes, the browser stops or data is cleared. It exists only in memory and is not restored after service restart. The approved root and each automatically dispatched resource have distinct durable authorization receipts. Duplicate clicks cannot renew or reset the grant. Existing DNS pinning, TLS checks, 8 MB per-request upload/response bounds, credential-scope validation, cancellation and the final pre-socket control check still apply. Expiry or revocation also prevents already-admitted work from sending later.

Scope comes from the host’s CDP frame, document-loader and resource metadata, never model/request fields. Matching Network metadata may arrive after Fetch interception; the broker waits up to 1.5 seconds, then falls back to exact review if it is missing. Already-authorized resources waiting to connect are not shown as new approval requests. The loader binding keeps an old document’s background traffic out of a new page’s grant. Chromium categorizes favicons as Other; the broker recognizes only the conventional `/favicon.ico` URL or an exact main-document icon declaration, using bounded DOM metadata queries without page-script evaluation. Unknown Other traffic stays on exact review. The model still receives no raw DOM, page scripts, DevTools connection, cookie values or owner screenshots.

This permission includes ordinary same-origin cookies and site-selected resource URLs. Even an image GET can change server state, and script/CSS URLs can contain data. The interface exposes the scope and limits; it does not claim that the allowed requests are read-only or that arbitrary private information is tracked. Broader semantic action classification, task-bound egress and taint handling remain open. Cross-origin CDNs and dynamic API calls still require review, so this reduces friction without establishing full Muse browser parity.

Nine additional Node cases cover explicit/typed consent, forged metadata, scope exclusions, expiry/count bounds, navigation/restart revocation, pre-socket cancellation, duplicate approvals and credential checks. `npm run computer:test:page-loads` adds six actual Chromium/HTTPS checks: resource loading, blocked cross-origin/frame/API requests, ended-action revocation, reviewed single form submission, document redirect review and exact-only fallback. The desktop/phone, packaged Mac and iPhone fixtures now include a real script, stylesheet, image and custom icon. Receipts are in `../relay-evidence/browser-page-load-runtime-acceptance.json` and the current platform acceptance files; the combined result is `browser-page-load-verification.json`.

`npm run computer:test:browser-ios` passes an actual iPhone 17 Pro Simulator journey on iOS 26.5 using the production WebKit client, HTTPS owner authentication, the native saved-server dialog, a real Relay worker, a controlled HTTP model, host Chromium and actual Docker/Colima containers. ## Remaining release requirements

- A separate restricted browser container now enforces the tested direct-network, resource, workspace and display boundaries. Continue hostile-page and browser/kernel escape analysis; these bounded checks are not an arbitrary-exploit defense.
- The Computer page and assistant tools are connected. Verify richer forms, frames, native devices, actual hosted models and accounts. Retain the prohibition on agent JavaScript evaluation, raw DOM, cookies, storage and DevTools access.
- Real Docker takeover/freezer and assistant-tool composition now pass with the independent HTTPS fixture. Broaden hostile-page, model-context and process-escape acceptance. Keep the runtime-only and UI-fixture scope separate from the actual-container receipt above.
- The explicit single-page resource scope is implemented. Broader task-sensitive review policy, CDN/API loading and semantic action classification remain. Neither GET nor same-origin access universally implies a safe read.
- Handling of non-cookie tokens, response-body credentials, localStorage/IndexedDB, SSO and explicit cross-origin credential scopes. Current exact-origin cookies can intentionally break cross-subdomain login flows. Known-string masking is not general secret redaction, and short secrets can over-redact text.
- Credential removal UI now clears request payloads and credentials after an inline confirmation; action identities remain for replay protection. Add finer retention controls, classifiers, prompt-injection defenses, taint tracking and smooth failure recovery.
- Live provider/account acceptance, physical-device/Android journeys and refreshed native release packages. Booking and merchant/amount-bound payments remain a separate unimplemented requirement.
