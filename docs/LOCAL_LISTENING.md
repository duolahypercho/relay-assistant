# Local listening

On a Mac running Relay (macOS 14 or later), open **Settings → Voice → Set up voice** to enable local listening and the installed Mac voice together. Both are selected only after installation succeeds. No microphone starts and no chat model is changed. **Voice options** keeps separate listening/speaking providers and Off controls available. If no chat model is connected, Relay explains that dictation is ready and offers **Connect AI** for voice chats.

For listening alone on a Mac, open **Voice options → Set up local listening**. On the supplied Linux server image, use **Set up local listening** directly. Relay shows the download before starting: approximately 202 MB on Mac, or 148 MB on Linux where the recognition engine is already included in the server image. One action installs the pinned multilingual Whisper Base model and any required runtime, verifies their bytes and selects local listening. Progress stays on the Voice page; leaving the page or reopening it does not create a chat message. Cancel stops setup, and Continue starts a fresh attempt. A server restart leaves interrupted setup stopped until you continue.

The microphone beside your message opens Voice settings directly if listening is missing; after setup, a fresh tap starts dictation. **Done** transcribes the recording and appends editable text to your existing draft. You choose when to send. Voice chat uses the same listening engine, your selected chat model and a separate speaking connection; **Use Mac voice** supplies speaking without an audio-service account. Starting a voice chat explicitly permits spoken turns to be sent automatically. Connected phones use the Relay server for recognition; keep it awake and reachable. Linux voice chat needs a separate speaking service; Mac system speech is available only on a Mac server.

**Listening connection → Off** stops using local recognition without removing its downloaded files or forgetting a saved audio provider. **Use local listening** reselects the installed model. A changed voice setting or active audio request during installation prevents late activation. Combined setup checks both connection revisions and selects them in one encrypted write; cancellation, an interrupted server, or a conflict enables neither connection. **Use local voice** makes a fresh explicit selection after a conflict; the completed files remain available. Manual audio endpoints remain available through Set up listening/Edit listening. On an unsupported server platform, choose an audio service instead.

## Audio handling and limits

Recognition runs in a separate bounded child process with no audio-service request. Browser dictation converts its native recording to a mono 16 kHz WAV in memory; this supports WebM desktop and MP4/AAC iPhone recordings without a server decoder. Live voice turns already use that WAV format. Uploaded compressed audio files need an installed FFmpeg on the Relay computer (or RELAY_FFMPEG_PATH); WAV and dictation do not. Relay does not install FFmpeg through this setup.

The server writes recording/PCM bytes to a private temporary directory, deletes them after success, error or cancellation, and never saves the original dictation audio into chat. Abrupt operating-system/process termination can leave temporary files until the operating system cleans its temporary directory. Voice-chat transcripts and generated spoken replies use the ordinary conversation storage. Audio remains subject to any configured chat provider once recognized text is sent to that provider.

Inputs are bounded to 8 MB and two minutes, one recognition operation at a time, and a 60-second recognition deadline. The helper rejects invalid samples and near-silence; empty recognition is retryable. Original dictation recordings remain in the open input control for retry. Closing it discards the recording. Cancellation kills only the owned process group and waits for exit before cleaning temporary files. Server errors do not expose internal paths or process output.

The multilingual Base model is a small general-purpose recognizer, not a speech-quality guarantee. Accuracy depends on language, accent, noise and pronunciation. Linux uses the CPU; Mac uses Metal where available. The first Mac request may be slower while Metal initializes; this development Mac's initial command probe took about 18 seconds cold and 0.27 seconds warm. Review dictated text before sending. Physical microphone, noisy-room, Bluetooth and broader-language acceptance remain open.

## Independent implementation and pinned dependencies

Relay's C bridge, installer, WAV conversion and UI are original code. No Muse, OpenMuse, Grok Bot or Dot source or artwork is included. The optional recognizer is the MIT-licensed general-purpose [whisper.cpp v1.9.2 runtime](https://github.com/ggml-org/whisper.cpp/releases/tag/v1.9.2), used through its public C API, with the MIT-licensed [Whisper Base model](https://huggingface.co/ggerganov/whisper.cpp). Upstream license notices accompany Relay and each completed installation.

`server/local-listening-artifacts.mjs` pins runtime/model URLs, exact sizes and SHA-256 digests. Runtime downloads follow only GitHub release-asset redirects; model downloads follow only named Hugging Face/CDN destinations over HTTPS. Stream size, archive digest and the exact extracted universal Mac library digest are checked. No archive path or symlink is installed, no shell/install script runs, and existing unexpected runtime directories are never overwritten. Temporary staging and downloaded model files use owner-only permissions. The same OS account remains trusted to manage its Relay data directory.

The Mac runtime lives under `data/runtimes/listening/1.9.2-base/`. It includes the original universal helper, verified library, model, receipts and licenses. The small helper is included in the Mac package; its upstream runtime and model are downloaded only when requested. Linux uses an architecture- and helper-digest-specific directory in the same listening folder. The server image includes a CPU-only helper statically linked to the pinned MIT whisper.cpp/ggml engine. Setup downloads only the model, verifies the bundled helper and writes a receipt; there is no Mac-framework extraction on Linux. A missing or damaged bundle leaves local setup unavailable.

Windows installation, automatic runtime updates, model selection, model reuse across engine-version upgrades and download resumption are not implemented. Existing runtimes are preserved when a different bundle is built.

Build the original helper on a Mac with Xcode command-line tools after obtaining the exact archive URL recorded in the artifact manifest:

```sh
node scripts/build-listening-helper.mjs /path/to/whisper-v1.9.2-xcframework.zip
```

The build verifies the archive before extracting only public headers into a temporary directory. It creates `native/audio/relay-transcribe-macos` for arm64 and x86_64 with a macOS 14 minimum. It links no upstream implementation into the bridge; runtime loading happens after installation. Arm64 is the tested platform; the universal binary's Intel slice is built but not runtime-certified.

The Linux Docker build verifies the source archive for whisper.cpp v1.9.2 commit `306c88f4d1286aec1bf96e544632897886af5501` before compiling the original bridge and upstream engine. `scripts/build-listening-linux.mjs` emits a bounded manifest and the upstream license beside the helper. Compiler file-prefix mapping removes temporary directory names from the helper, and two independent builds with the same toolchain must produce the same manifest/digest. The build enables no native-host instruction tuning; ARM64 targets ARMv8-A and the x86_64 path disables optional AVX/FMA/F16C instructions. Linux ARM64 has runtime acceptance; the AMD64 build path is not yet runtime-certified. Standalone Linux checkouts must supply a matching built bundle or use the Docker image.

For automated checks, use `node --test tests/local-listening.test.mjs tests/voice-connections.test.mjs`, and the `voice:quick:test:ui`, `voice:quick:test:recovery`, `voice:quick:test:mac`, `voice:quick:test:ios` and separate local-listening scripts. Acceptance fixtures require the verified runtime ZIP, Base model and an original synthetic `probe.wav` in `../../work/local-listening-research`. They never use the owner's workspace, hardware microphone or model account. See VERIFICATION.md for results and limitations.

Linux acceptance runs through `npm run voice:linux:test:ui` and `npm run voice:linux:test:ios` against a disposable Docker engine containing built `relay-server:local` and `relay-https:local` images. Set `DOCKER_HOST` and, if needed, `DOCKER_CONFIG` to that engine; `RELAY_TEST_DOCKER` is the Docker executable path. The tests use actual HTTPS and Linux recognition, with an original synthetic microphone input and controlled chat/speaking services. Only `probe.wav` is needed locally; setup downloads the real model. Never target an owner deployment with these fixtures.
