# Relay’s private computer

The agent and owner share an independently implemented Linux desktop, with Python, Node, git, Chromium for approved websites and local previews, Mousepad, xterm and the LibreOffice document apps. On macOS, Docker runs inside a Linux VM such as Colima. On Linux, the desktop is a container, not a separate kernel or a hostile multi-tenant sandbox.

For a hosted Relay server, an administrator can connect a **dedicated separate Linux VM** through pinned mutual TLS. Desktop, commands, files, restore points, the private browser and local MCP pipes keep their existing interface. The application host receives no Docker socket. The connection grants the entire dedicated engine, so this VM must be exclusive to the workspace. See [remote computer setup](REMOTE_COMPUTER.md).

## Returning a computer file in chat

Ask Relay to finish a task on its computer and attach the result here. For recognized explicit local-delivery requests that refer to a screen, window or visible controls, Relay inspects the current private screen before planning when available. File-only work starts from the supplied sources and a small verified computer power-state snapshot without an unrelated desktop image. This avoids starting an already running desktop merely to learn its state; screen tools remain available if the model needs to inspect it. The snapshot includes only enabled/state/controller/network fields, is checked across control ownership, and grants no action permission. This does not start an app, change the desktop or create a chat event. Owner takeover still prevents observations. Models known to lack vision receive only the optional observation’s text metadata; owner-supplied images and explicitly requested screen tools still require image support. Unsupported or asleep computers retain the normal guarded tool path.

If an export path is missing, Relay checks the two workspace download folders for the exact filename and returns location hints without attaching or substituting a file. An export returns a bounded plain-text preview when available so the model can check the actual result and answer the remaining parts of the request. A completion claim alone cannot satisfy this delivery check. Relay requires an actual export from the current request, a file card, and matching saved bytes. It privately asks the model to finish remaining work before claiming delivery. Another continuation requires intervening successful computer-tool work, with at most three corrections. Consecutive unsupported claims fail honestly. These requests have four additional tool rounds for locating/exporting results. If the limit is reached before delivery, the existing **Try again** action resumes the saved context with four additional rounds; reloads and server restarts grant no new rounds. Existing uncertainty and takeover checks still prevent blindly replaying actions.

The check recognizes direct English and Chinese requests to return a computer file into this chat. It excludes quoted source, advice, negated delivery, external sends, connected-app requests, routines and assistant handoffs. This is a file-presence safeguard, not proof that every requested edit is correct or that all requested outputs have been produced. Actual output content still needs inspection. Screens and files cannot grant permission for unrelated or external actions.

IDs for desktop actions, commands, file writes and directory creation are optional for models. Relay derives a durable ID from its own tool-call identity when omitted, and returns `retryOperationId` for an exact retry. Explicit IDs retain their existing behavior; different arguments under the same ID are rejected. This removes model bookkeeping without weakening receipts or changing the owner input protocol.

## Document apps

In **Computer → Files**, choose **Document**, **Spreadsheet**, or **Slides** to start a blank file, or **Open** beside an existing file. Controls appear on an updated computer while you have control. See [document apps](COMPUTER_DOCUMENTS.md) for supported formats, saved-file behavior and verification.

## Resume directly from chat

When the assistant is paused for owner control and the configured computer is asleep, chat offers **Start & resume**. One explicit action wakes its existing selected Colima profile if necessary, opens the saved desktop, verifies readiness and then gives control back. A stopped desktop on an already running engine uses the same action without starting another VM. A running desktop retains **Give back to Relay**. Startup remains in the compact chat status area, with progress, inline failure/retry and **Open computer**; it does not add messages or replace the draft.

**Cancel resume** keeps owner control. It can cancel the wake or cancel the promised handback while desktop opening finishes. Once actual handback begins, the cancel button is withheld until the atomic control change finishes. Cancellation never stops a shared VM. If another takeover, Stop, restore or shutdown changes the computer-control epoch, the pending resume cannot hand back. Readiness failure or failed runtime unfreeze also prevents success. The authenticated, same-origin owner API exposes this action; the agent has no startup/resume tool.

Progress survives page navigation, reload and mobile-client relaunch while the server continues running. Restarting the server drops any unfinished resume intent and retains owner control; it never infers permission to resume from saved status. Ordinary **Start computer** on the Computer page continues to open under owner control and cannot be silently upgraded by a concurrent resume. Existing setup, profile, image, filesystem and network boundaries apply.

The acceptance commands `computer:resume:test:ui`, `computer:resume:test:mac`, `computer:resume:test:local-mac` and `computer:resume:test:ios` require an explicit existing stopped profile through `RELAY_ENGINE_TEST_PROFILE`. They use their own workspaces and a controlled model (sample mode for the own-backend Mac case), wake real Colima/Docker, and restore the profile's stopped state without editing its configuration or the active Docker context. See VERIFICATION.md and the sibling `chat-resume-*` receipts for completed runs and platform limits.

## Start once

For an existing engine, open **Computer → Set up computer**. Relay checks the local Docker/Colima engine, prepares its own desktop image, verifies its files and runtime as the non-root desktop user, and saves the setting. If its existing Colima profile is asleep, the same button wakes it and continues setup. Choose **Start computer** when setup finishes. No `.env` edit or server restart is needed, including in the packaged Mac app. On a phone connected to a Relay server, setup runs on that server, not on the phone.

The page shows progress, **Cancel setup**, and an inline retry when something fails. You can leave the page and keep chatting; returning or reloading shows the ongoing setup. Setup never adds chat messages or changes your draft. Downloads/build layers may remain after cancellation so a later attempt can reuse them. A disposable runtime-check container is explicitly cleaned up.

On Apple silicon Macs running macOS 14+, a fresh server can now use **Set up computer** to install verified private tools, create its own VM and open the desktop. It needs 8 GiB memory and 40 GiB free disk space. Progress, cancellation and retry stay inline; no host folders, global Docker context or owner Colima profile are changed. See [private installation](COMPUTER_INSTALLATION.md) for releases, storage, lifecycle and verification limits. Other server platforms need Docker (or Colima plus its CLI) installed separately. Existing local engines retain the discovery and recovery behavior below.

For an already configured computer, **Start computer** wakes its selected existing Colima profile and opens the saved desktop. Relay keeps the configured Docker socket pinned, checks that the matching profile still exists at dispatch, and uses fixed Colima flags that preserve profile configuration, the active Docker context and SSH configuration. This owner-only action is not a model tool. While it is offered or running, the page hides competing repair controls. The page shows progress; you can leave, reload or keep chatting. **Cancel startup** is available while waking/preparing; once desktop opening begins, use the normal Stop control afterward. Cancelling or quitting Relay does not stop a shared VM, and a partly started runtime may remain running. Restarting the server does not replay an interrupted startup action: return to Computer and inspect its current state.

Only the nine bundled original `docker/` source files enter the temporary build context, including when extracted from the Mac app archive. Their bytes and fixed file permissions determine a versioned image tag. The validated image/socket are stored privately in SQLite and restored on server/app restart. `RELAY_DESKTOP_ENABLED=false` disables in-app setup; `true` preserves manual operator configuration. Leave it unset for in-app setup. Existing saved images are not automatically replaced by a later app build; use Computer care to review and apply the bundled workspace update.

For operators, the CLI remains available:

```sh
npm run computer:setup
npm run dev
```

On macOS, `brew install colima docker` supplies an open-source runtime. The CLI can start a dedicated `relay` Colima profile with 4 CPUs, 4 GiB RAM, a 24 GiB data disk and no host directory mounts. It does not install a login service or change the active Docker context. The image is built from Debian packages, not another assistant’s code. The CLI writes `RELAY_DESKTOP_ENABLED=true`, `RELAY_DESKTOP_IMAGE=relay-desktop:local`, and, when using Colima, its Docker socket to `.env`. Other environment settings are preserved. Packaged-app operators can supply manual settings in `server.env`; ordinary local setup uses the page instead.

Open the computer icon in the chat header, or **My computer** in the plus menu. **Start computer** starts its saved workspace and waits for the desktop window before showing Ready. With a configured vision-capable model, asking for computer work in chat lets the agent start it itself. The default sample assistant is deterministic and does not plan arbitrary computer tasks.

The agent's `computer_start` tool now returns the current desktop image when startup reports it running, including apps that were already open. It uses the same image transport and owner-control checks as a normal screenshot; image bytes stay out of textual tool results. An owner takeover while that screenshot is pending discards it. The public website tool is explicitly described as an HTTP/HTTPS opener: existing local apps and files work offline through the desktop tools and do not require website permission.

On updated computers, agent screenshots also include bounded, read-only control names, roles and positions from the focused app when it exposes Linux accessibility data. Chromium is enabled for this; unsupported apps retain the screenshot fallback. The agent receives normalized positions with the screenshot and must check the current screen before acting. Labels are untrusted app content, and toolkit visibility does not prove that another window has not covered a control. This observation does not call accessibility action, text-value or editing APIs. Password widget names and children are excluded; ordinary visible page text remains observable. Collection is limited to 80 controls, a bounded tree and a short timeout. Takeover discards both pending metadata and screenshots.

The accessibility bus lives only inside the desktop, with no host permissions or new published ports. It is not mounted into the separate command runtime. Ordinary owner screen polling does not collect these hints. Action receipts retain acknowledgements without screen metadata; an exact retry does not return old control positions. Existing saved computer images require an explicit workspace update through **Computer care**; installing Relay alone does not replace them.

Run `npm run computer:setup:test:ui` and `npm run computer:setup:test:mac` for browser/phone-layout and packaged local Mac acceptance against real Docker. The latter includes a full app quit/relaunch. `npm run computer:lifecycle:test:ios` also verifies native iPhone Simulator setup, cancellation/retry, command-created files, reviewed update, relaunch, actual frozen-display recovery, handback and preserved chat draft through an isolated HTTPS backend. Use `RELAY_ENGINE_TEST_PROFILE=<existing-profile> npm run computer:engine:test:ui`, `computer:engine:test:mac` or `computer:engine:test:ios` for explicit stopped-Colima acceptance. These tests require a selected existing stopped profile, remove only their isolated workspaces and restore the profile to stopped. Runtime installation, Windows named-pipe engines, physical phones and Android remain separate checks.

## Updates and recovery

If previously verified workspace storage disappears, Relay shows **Needs recovery** instead of opening an empty computer. Recovery controls open directly below the explanation. Restore a saved point or import a portable backup; if you want to begin again, **Start a new empty workspace** opens an inline review before creating separate storage. Cancelling keeps the original location selected. Chat history and restore points remain intact. Chat also offers **Recover computer**, and sending a normal message can continue the conversation without creating or replacing computer storage.

An unreachable engine is a connection problem, not proof that files are gone. Detection requires a successful engine listing and remembered evidence of prior storage: a verified volume, or on upgrade a completed computer operation/restored workspace. An older installation with neither evidence cannot establish that storage disappeared before this version first observed it. First-time setup can still create a workspace. Recovery cannot restore unsaved application memory or reconstruct deleted files without a surviving restore point or portable backup. See [portable backups](COMPUTER_BACKUPS.md).

Open **Computer care → Check for updates** on the separate Computer page. For a computer set up in Relay, this prepares and checks the workspace software bundled with the current Relay app. Your existing desktop remains usable during preparation. **Not now** discards the review without restarting; reloading retains it while the server stays running. If the source version is unchanged, the page reports that it is current.

**Restart & update** is an explicit inline review: open applications and jobs close, and unsaved work can be lost. Saved workspace files and the browser-profile directory remain in the same owned volume. Relay pauses assistant dispatch, invalidates older computer observations/input, closes website grants, replaces the desktop and command containers, and leaves the new command runtime frozen under owner control. Inspect the result, then choose **Give back to Relay**. Teaching recordings end before replacement. Interrupted jobs are recorded as interrupted, never silently rerun.

When the desktop cannot be observed or reports an error, **Review recovery → Recover computer** offers the same saved-file-preserving replacement using the currently configured image. It is shown from the Computer error state. This can recover a broken display or desktop process; a stopped existing Colima profile has the startup flow above, while other runtime failures, disk corruption or changed isolation settings require server-side repair. Unexpected containers or mounts are rejected before removal.

If a prepared update fails to start, Relay attempts to restore the previous image and durable configuration. A successful rollback is reported explicitly and stays under owner control. If restoration itself fails, the page reports the error instead of claiming recovery. File/profile bytes stay in place; this is not a snapshot, backup, browser-profile downgrade guarantee or restoration of unsaved buffers. The database image setting is committed after the old container is removed and before the new one starts, so a subsequent server start selects the intended saved image. Interruption during an image update and physical host power loss remain untested. Forced VM restart of completed and partly executed task work is covered below.

Computers configured explicitly through operator environment settings support recovery, while image updates remain with the operator. These controls do not download a new Relay app or upgrade the host OS/VM. They require the existing authenticated owner session and same-origin POST; model tools cannot invoke maintenance. Review tokens prevent replaying an old update/recovery action.

Run `npm run computer:maintenance:test:ui`, `npm run computer:maintenance:test:mac`, `npm run computer:maintenance:test:rollback`, and `npm run computer:lifecycle:test:ios`. Browser and native iPhone Simulator tests use actual image/container replacement and freeze a fixture display to exercise recovery. Mac acceptance uses the bundled local backend and a full app relaunch. The rollback test builds a deliberately broken startup image, then verifies restoration and saved-file bytes.

## Restore points

Open **Computer → Restore points → Save restore point** to keep a dated copy of the workspace files and browser profile. Saving briefly freezes desktop writers while copying; the existing desktop is retained. Foreground computer actions are interrupted and the command runtime stays paused under owner control. Save unfinished work in its application first: a restore point contains saved disk files, not application memory. Saving and managing points adds no chat messages.

**Restore** opens an inline review. Applying it closes apps and jobs, copies the chosen point into a new private workspace volume, and starts the current computer software with those saved files. Files created after the chosen point are absent from the restored copy. The previous workspace becomes an automatic **Before restore** point, so you can restore it to return to the later saved work. Chat history, attached chat files, account/model settings, and the computer software version are not rolled back. Relay remains paused until you choose **Give back to Relay**.

The saved-point volumes are never mounted into the agent's normal desktop or command runtime. Capture uses a non-root helper with no network, a read-only root filesystem, no capabilities, a read-only source volume and one new destination volume. It preserves symlinks without following them, skips transient Unix sockets, and rejects device files/named pipes. A point supports up to 8 GiB and 200,000 entries; a copy has a five-minute runtime bound. Ten saved points are retained at most. **Remove** has its own inline review and permanently removes only that saved copy, leaving the active workspace untouched.

The active volume pointer and automatic before-restore point commit in one SQLite transaction. If the restored desktop fails to start, Relay attempts to reattach and start the previous workspace. An interrupted operation keeps a private journal: startup reconciles its own helper, thaws its own paused desktop, and removes only an unfinished copy. If reconciliation cannot finish, computer actions stay blocked and **Finish interrupted operation** offers an explicit retry. The service drains active copies during graceful shutdown.

These are copies on the same Docker engine. Losing the engine/disk also loses its saved points. Choose **Save backup to a file** to export a password-protected [portable backup](COMPUTER_BACKUPS.md), or **Import backup** to select a file and review it before restoration on a prepared computer. The command-line workflow also remains available. Browser sign-ins may expire independently; live account/profile compatibility, physical phones and native Android restore-point interaction acceptance remain separate gates. Native iPhone Simulator save/review/restore/relaunch/undo/removal and handback acceptance now passes. Run `npm run computer:snapshots:test:ui`, `npm run computer:snapshots:test:runtime`, `npm run computer:snapshots:test:mac`, and `npm run computer:snapshots:test:ios`. The native Mac test uses the packaged local backend, restores, fully quits/relaunches, and restores the automatic previous point. Runtime tests exercise an actual failed desktop startup and rollback, a persisted interrupted capture with a frozen desktop, and the size limit.

## One handoff

The page shows a live screenshot while open. During owner control, model tools cannot observe the screen, read computer files, or inspect command output; already-started observations are discarded if control changes. **Take control** cancels the current computer command and pauses assistant model/tool dispatch, queued requests, delegated tasks and new scheduled/monitor work. In-flight read-only monitors are cancelled. An external write already accepted by a provider is allowed to record its outcome once; it is never blindly retried. Control ownership survives reload and server restart. **Give back to Relay** continues waiting assistant work. It is also available when the desktop is stopped. Replies planned across the handoff are discarded and replanned; pending computer input based on an old screen is not executed. An interrupted command is not automatically replayed. The agent sees fresh screenshots as model image parts. Screen images are not inserted into permanent chat history.

Click the displayed desktop and type directly. Drag to move a window or select text, double-click to open, or right-click for a menu. Fast typing, clicks and shortcuts are delivered in order. A failed or uncertain input stops the remaining queue; it is never automatically replayed. Direct text entry supports composition and explicit local text paste, up to 4,000 characters per insertion. Unicode and long text use a temporary clipboard inside the guest to avoid X11 character loss; this replaces the guest selection and releases it after delivery. Local clipboard contents are not synchronized or read in the background. Tab leaves the desktop so keyboard navigation remains available. The control strip provides an alternative text field, Enter and Tab, including for a phone keyboard. That field disables automatic capitalization, correction and spellchecking; a successful send clears it and dismisses the touch keyboard. A failed send keeps the text. **Zoom in** opens a scrollable full-resolution view; **Fit screen** restores the overview. On touch screens, drag within the fitted desktop to move/select; in zoomed view, swipe to pan and tap to click. Mouse dragging works in either view. Commands are tucked under **Commands & activity**. Closing the app’s window leaves its server running. Fully quitting or restarting Relay also leaves the existing desktop and open apps in place, even with no registered background job. Offline programs can keep running while Docker remains up; commands remain frozen if the owner has control. Foreground commands are cancelled and website grants end with the server. Model responses, reminders and scheduled assistant work require the Relay server. You can also choose **Give back to Relay** in the chat’s pause notice to resume waiting work without opening this page. **Stop computer** explicitly closes its apps and jobs, retaining saved workspace files; starting afterward launches fresh processes. A Docker/VM shutdown or container replacement does not preserve unsaved application buffers.

Run `npm run computer:test:restart` for actual server-process restart acceptance: an unsaved editor buffer survives, the same command processes remain frozen during owner control, handback resumes them, old website grants expire, and explicit Stop closes processes while retaining saved files. This uses isolated real Docker containers, not a simulated shutdown.

## Copy and paste

While you control the computer, select text in its app and choose **Copy** below the screen. Desktop **⌘/Ctrl C** and **⌘/Ctrl X** also transfer copied/cut text to your device. Paste from your device with the normal paste command or the phone text field. Clipboard transfer is explicit; Relay never polls your device clipboard. It adds no chat message or model request.

Terminals use their selected text for Copy. In xterm, **Ctrl C** still interrupts the running command; **⌘ C**, **Ctrl Shift C**, or the Copy button copy instead. Terminal selections cannot be cut. Other applications use their normal Copy behavior, including their existing guest clipboard when Copy leaves it unchanged.

Transfers accept up to 64 KiB of UTF-8 plain text. Images, files and rich formatting use the file/photo workflows instead. The guest copies and validates text before attempting Cut, so an oversized or unsupported selection is not removed. If the device denies clipboard writing, the text stays in an inline field with **Copy to device** and **Dismiss**; retrying that field never cuts or copies the guest again. The field is cleared when you leave the page or give back control. A failed/lost Cut response is not retried automatically; inspect the guest before repeating it.

Copy follows pending typing and pointer input in order. Navigating away cancels delivery of an unfinished transfer; handback invalidates the server result. The owner-only endpoint requires the existing authenticated session and same-origin POST, returns `no-store`, and does not store clipboard bytes in chat, teaching or computer-operation receipts. Copied material can of course still exist in the guest application and in your device clipboard after a successful explicit copy.

Run `npm run computer:test:clipboard`, `npm run computer:test:clipboard-mac`, and `npm run computer:test:clipboard-ios`. These exercise the production controls against a real isolated Docker desktop. The iPhone test uses native WebKit and the system Paste menu; it is Simulator acceptance, not a physical-phone or Android claim. The latest completed checks are in [VERIFICATION.md](VERIFICATION.md).

## Files and actions

Files in `/workspace` and the Chromium profile under `/workspace/.home` survive stopping the container. Take control, then drop individual files onto the desktop or choose **Add files from your device**. Files go straight into the currently open workspace folder; there is no intermediate library step or chat message. Duplicate names become `name (2).ext` instead of replacing existing content. Up to eight files can be added at once, each no more than 8,000,000 bytes. Folders are rejected. A failed batch stops with an explanation and leaves successful copies intact.

**Files** opens the folder list; **Copy here** imports a chosen Relay file and **Save to Relay** brings a result back into the normal file library. Agent tools use the same bridge. Transfers refuse symlinks and path traversal and do not overwrite existing destinations by default. Direct device uploads require a running computer under owner control; they do not take control, start the computer or send a message automatically. Device clipboard transfer happens only through the explicit Copy/Paste controls above.

`npm run files:test:ui` checks device uploads and exact round-trip bytes against isolated real Docker desktops on desktop and phone browser sizes. `npm run files:test:mac` runs the same journey in the packaged Mac remote client. The file input and DOM drop paths are exercised; operating-system Finder gestures and native phone file pickers are separate checks.

After rebuilding the desktop image, stop and start the computer to use it. Relay replaces the stopped container while preserving its named file volume and control ownership; it never replaces a running desktop underneath ongoing work.

Computer operations have durable IDs and receipts. An identical successful retry returns its saved result without executing again. A changed request with the same ID is rejected. Interrupted work is never automatically replayed. Commands have a 60-second ceiling and a combined 128 KB output limit. Cancellation and timeout kill the command’s process group. Agent commands now run in a separate container, including their detached applications. Takeover freezes that container with Docker’s kernel freezer; handback resumes the same processes. Stopping removes it while frozen, without briefly resuming background work. Owner commands and the built-in desktop browser remain in the desktop container and stay available. An agent-launched graphical app is paused with its command runtime until handback.

## Longer work in the background

`computer_job_start` launches a named job and returns a compact progress card. Ordinary jobs yield to the conversation immediately; interactive jobs let the model inspect and answer the running program in the current tool loop. `computer_job` lists jobs from the current conversation, reads retained output, or stops a job. A completed job queues a continuation of the frozen original request once; it adds no synthetic user message. The agent can inspect the result and export its file without asking the owner to repeat the request. Jobs and their logs also appear under **Commands & activity** on the separate computer page. **Stop job** works directly from the chat card, including during owner takeover.

The supervisor runs inside the command container and survives a Relay service restart while that container stays alive. Relay reconnects using the saved job ID, container ID and boot identity. A stopped, replaced or lost runtime produces an interrupted result; it never causes an automatic command replay. Lost launch acknowledgements are resolved by inspecting the same ID. Completed-job continuation is withheld when the original request was cancelled, the conversation was archived, or its bound account changed. An owner Stop also cancels any pending continuation.

At most four jobs run at once. Each has a one-day maximum wall-clock limit (one hour by default), and the latest 32 KB of each stdout/stderr stream. Input is closed unless the job explicitly enables interactive mode. Earlier output is discarded with a visible truncation label. The newest 64 finished records retain their context/output; older records keep a small identity tombstone to prevent replay. A continuation chain is limited to twelve jobs. Logs are private server data, excluded from the general workspace snapshot, and treated as untrusted source material. Time spent frozen still counts toward the wall-clock limit; an expired job is ended when it resumes.

Cancellation and timeout terminate the supervisor’s process group. Programs that deliberately create a separate session can escape that per-job group; **Stop computer** still terminates the entire command runtime, and takeover still freezes it. Resuming live processes after a VM/container restart and managed installation remain outstanding. Finishing a tracked shell does not imply that deliberately detached subprocesses have finished.

## Interactive programs

Set `pty: true` on `computer_job_start` for a real pseudo-terminal. The program receives terminal stdin/stdout/stderr, a controlling terminal and a fixed 100-column by 30-row size. Its merged output uses the same bounded tail as ordinary jobs. `computer_job_input` sends UTF-8 text (include a newline to submit), Ctrl-C (`\u0003`) or EOF (`\u0004`). Each input is limited to 4,096 bytes; a session accepts at most 256 input operations. This supports interactive command-line programs; the job details are a text log, not a full-screen terminal emulator.

The owner can expand **Details & output**, type a reply, and choose **Send input**, **Interrupt**, or **Finish input**. The main chat draft stays intact. Terminal drafts and an unconfirmed input ID are kept in the current tab's session storage across reload; completed jobs clear that entry. No input is sent if the tab cannot save its receipt. These fields are not a credential channel or vault: terminal echo/output may contain what was entered.

The guest records input intent before writing to the terminal. Retrying the same operation ID and exact bytes returns its saved acknowledgement; changed bytes are rejected. A crash or partial write leaves an uncertain receipt that refuses replay. “Accepted” means bytes reached the terminal, not that the intended action succeeded. Terminal input requires the same runtime and an active owning request for model actions. Takeover blocks all input into frozen jobs until handback; Stop still works while frozen. Agent observation of an inline-completed interactive job suppresses a redundant background continuation.

Run `npm run computer:test:interactive` for real terminal/Unicode/interrupt/EOF/restart/takeover checks, and `npm run computer:test:interactive-ui` for actual desktop/mobile UI, lost-response retries across reload, retained drafts, file results and accessibility checks.

## Websites without direct guest networking

Website access is enabled with the desktop by default. Set `RELAY_DESKTOP_WEB_ENABLED=false` for an entirely offline desktop. No website is granted automatically.

When the agent needs a website, its chat card offers **Allow & continue**. That owner action grants the connection for at most one hour and resumes the frozen original request once. It creates no synthetic user message and preserves the current draft. Decline leaves it blocked. A reused card cannot enqueue duplicate work. **Websites** on the separate Computer page also lets the owner add, allow, open and revoke connections. Background traffic and third-party resources stay blocked without manufacturing approval cards. A page may require additional resource hosts; the owner or agent must request each deliberately.

A Python loopback proxy in the guest exchanges bounded frames with a Node broker over Docker stdin/stdout. The container still uses `--network none`; there is no routable guest interface or published proxy port. The server resolves every outbound connection, rejects private/reserved IPv4 destinations and nonstandard ports, then connects to the checked address. HTTP and end-to-end HTTPS work, including downloads. The broker permits at most 32 connections, 64 MB per connection, 30-second idle time and five-minute connection lifetimes. Revocation or expiry closes active connections. Stop and server restart end grants; downloaded files and the browser profile remain.

A website grant is a **network connection capability**, including forms and uploads. It is not an exact-action, URL-path, credential or payment review. HTTPS is tunneled rather than decrypted; the broker does not inspect encrypted methods, content, alternate HTTP authorities or application behavior on shared hosting. These permissions must not be represented as Muse’s Sentinel, taint tracking or credential-surrogate architecture. Runtime code can use the approved endpoint too. Normal task intent still governs agent use; supported mail/calendar writes use exact connector reviews, while other consequential steps require owner takeover. Generic browser-write enforcement and a separate credential vault remain unfinished.

Browser cookies and files reside in the computer’s persistent profile. They are not isolated from code running inside that same computer. Takeover pauses new agent tools and observations and freezes the separate agent command container, including double-forked descendants. This is a process-lifecycle boundary, not complete browser isolation: both containers still share workspace files, the X display and the desktop’s loopback network namespace. Browser JavaScript, owner-launched programs, and work induced through desktop applications are not covered by the command freezer. Do not claim secret-vault isolation for this shared browser. No real account login, purchase or external form submission was used in acceptance.

## Resume without repeating completed work

Each live agent run has a private SQLite checkpoint containing its model/tool history, completed results and next step. Screen images are omitted. The journal is bounded to 12 MB per active run, excluded from browser snapshots, and removed after completion/cancellation/failure. If the server restarts between completed steps, the run continues from the saved boundary. A tool action interrupted before its outcome was saved requires inspection and an explicit retry; Relay does not guess that it is safe to repeat. A saved final response commits once without another model call. Restored computer plans must observe the screen again.

The chat displays one pause notice outside the transcript. Queued messages get a small waiting label and cancellation control on their own bubble. Taking control, navigating, reloading and handing back create no chat messages and preserve the draft.

When the selected local Colima VM is confirmed stopped, the pause notice offers **Continue chatting**. This explicitly hands control back and resumes queued assistant work while leaving the computer asleep. **Start & resume** remains available alongside it when you need the computer. A running or unknown engine keeps the normal handback flow. An unreachable Docker socket alone never qualifies as a sleeping computer: Relay rechecks the exact pinned profile at dispatch, inside the serialized control boundary, and rejects changed control, cancellation, maintenance or interrupted restore operations. No runtime start, thaw or computer action is performed by Continue chatting. Computer-dependent work still needs its computer started; the existing command freezer and epoch invalidation remain in force.

## Boundaries and current limits

- The desktop and command runtime have no routable guest interface, published VNC port, host folder mounts, Docker socket, model keys or connector tokens. Approved web connections use the broker described above. Screens and input pass through the authenticated Relay API and Docker stdin, not a public desktop link.

## Runtime recovery

Control changes are acknowledged only after Docker confirms the corresponding pause/resume state. A failed pause leaves assistant work paused and rejects owner input; a failed handback retains owner control. Reopening Relay with saved owner control reconciles the actual kernel state before enabling interaction. Overlapping Take control/Give back requests respect the latest request. A stopped or replaced desktop gets a fresh command runtime attached to that exact desktop boot.

**Stop computer** sends fatal signals to workload processes while the runtime is still frozen, then removes it. The short-lived helper has the same unprivileged UID, no capabilities, no mounts and no network; it joins only the verified command PID namespace. This avoids Docker’s normal removal path briefly thawing child processes after signalling only the container init. If the helper fails, Relay leaves the runtime frozen and reports the error instead of resuming it to force cleanup.

## Using the desktop on a phone

The live screen and typing controls come first. Swipe over the screen to scroll the page; tap to click inside the computer. Turn on **Drag** to move windows or select text, then turn it off to scroll again. **Zoom in** opens a pannable view and turns Drag off. Giving control back to Relay also resets Drag. With a mouse, dragging works directly.

Tap the keyboard icon beside the typing field to type directly on a selected guest field. Keystrokes, Backspace and Return go through the same ordered input queue as desktop input; there is no separate Send step. **Done** closes the keyboard and restores any unsent text in the separate typing field. On touch devices, live typing temporarily hides the large app header and bottom navigation to leave room for the guest; Back to chat and Done remain available. Losing control, stopping or leaving the page closes live typing and discards unsent queued input. The app never opens the keyboard merely because you tap the desktop.

Composition stays on the device until committed. Closing the keyboard or losing control discards unfinished composition. A local invisible sentinel allows mobile deletion events after sent text has been cleared; it is removed before guest delivery. This is a keyboard control, not automatic clipboard or dictation synchronization. The separate typing field remains available for reviewing a block of text before sending it.

The typing field, Copy, Enter and Tab sit together below the screen. Teaching, files, commands, and maintenance remain on this page, without adding messages to your chat. The computer's status sits beside its takeover control. Stopping the computer closes its apps and jobs and keeps saved files.

`npm run computer:test:keyboard` exercises phone/tablet layouts, soft-input semantics, composition, preserved text and control changes against a controlled guest boundary. `npm run computer:test:direct` tests Unicode, deletion, Return and existing mouse/drag behavior against a real guest; add `-- --mac` for the packaged Mac client. `npm run computer:test:keyboard-ios` runs the actual iPhone Simulator keyboard against the isolated Linux editor, including relaunch and handback. Physical devices and all OS input methods remain separate gates.

## Screen coordinates across models

The desktop and owner input API use 1280×800 pixels. Detected local Ollama `qwen3.5` and `qwen3-vl` vision connections receive a computer tool contract using normalized 0–1000 coordinates, matching those models’ documented grounding convention. Relay records that contract on the actual responding model’s tool call and converts at the agent execution boundary. This preserves the correct units through fallback and queued work. Invalid ranges or contradictory units fail before desktop input. Other connections retain the pixel default and can explicitly select normalized coordinates per action; Relay does not guess units from a number or custom model alias.

`computer:test:live` runs a real local vision model against a real isolated desktop. It asks the model to read randomized screen-only facts, select two checkboxes, leave a third unchecked, save through the GUI and attach the actual file. The harness verifies window event history and guest/exported/downloaded bytes, then checks separate-page navigation, owner takeover and draft persistence. Use `--mac` for the packaged client and `RELAY_COMPUTER_TEST_TIMEOUT_MS` to record an explicit task budget (default 300 seconds, bounded to 60–900 seconds). The Mac test selects a download destination using Electron’s API; the system save picker is outside its scope. It requires an explicit test Docker socket, installed desktop image, local model and dedicated model cache; it never configures the owner workspace. This is a bounded acceptance task, not a general computer-agent benchmark.

The agent file/command tools distinguish the desktop home (`/workspace/.home`, with standard browser downloads in `Downloads`) from the command runtime home (`/workspace/.runtime-home`). They instruct the model to list and verify the actual app-generated file before returning it, rather than invent a replacement when the first path is missing.

Agent keyboard input accepts common browser and X11 names, including `Enter`/`Return`, `Backspace`/`BackSpace`, arrow and page keys, and case-insensitive modifiers such as `Ctrl+a`. Relay canonicalizes a single allowlisted chord before guest execution. Arbitrary sequences, control characters, repeated/unknown modifiers and unsupported keys fail before input. Literal text still uses the separate typing action. Typing inserts into the focused field; an agent request that also supplies pointer coordinates is rejected before any input, with guidance to click or Tab first. This prevents coordinates from being silently ignored while text goes to another field.

## Interrupted task recovery

New task checkpoints can recover a confirmed private-computer action after the Relay service stops between saving its action receipt and recording the next step. Recovery reads the exact receipt bound to the request, operation ID and arguments; it never sends that action to the guest again. This covers commands, desktop input, ordinary file writes and directory creation. Remaining calls in the old batch are discarded, screen observations are refreshed, and newer owner instructions apply after the completed result is retained. Owner control, cancellation and worker leases still gate recovery.

A missing, interrupted or mismatched receipt stops the request with an explanation. A completed command with a nonzero exit code remains a recorded failure. Older checkpoints keep their original conservative behavior. Combined write-and-attach, imports, Office transformations and file exports are excluded from this new acting-checkpoint recovery because their output transactions or derived inputs need additional reconciliation. They must not be blindly repeated.

`scripts/test-computer-interruption.mjs` requires an explicitly selected, running, empty `relay-live-acceptance` engine and an installed Relay desktop image. It kills only its fixture worker with SIGKILL and force-stops/restarts that dedicated ARM64 VM. A confirmed command's fsynced file survives and returns once in the original chat; a partly executed command preserves its first effect, is reported as uncertain and is not rerun. The harness verifies no host-folder mounts, unchanged Docker context and unrelated VM status, and removes its own containers, volumes and database. It uses controlled model decisions: this is durability acceptance, not general model reasoning, physical host power-loss, disk-corruption or unsaved-app-memory recovery.
