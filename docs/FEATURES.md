# What Relay does

Missing previously verified computer storage now opens inline recovery instead of silently becoming an empty workspace. Restore a saved copy, or explicitly review starting afresh. Your chat and draft remain intact, and ordinary chat can continue while computer recovery waits. See [computer recovery](COMPUTER.md#updates-and-recovery).

The updated private computer includes office apps and can read Word, Excel, PowerPoint and PDF files directly for chat requests. Its existing Files section opens documents, spreadsheets, slides, PDFs and text, or creates a blank office file in one tap. App controls require owner takeover and add no chat history. See [computer documents](COMPUTER_DOCUMENTS.md) for update steps, test evidence and limits.

Everyday replies now share a concise default across action-capable and chat-only models, without new setup, removed tools or forced truncation. Real-model Main-chat follow-ups, requested files and side-chat recall have expanded acceptance coverage; model wording and response-time limitations remain. See [conversation verification](VERIFICATION.md#everyday-chat-and-continuous-conversation-acceptance--october-14-2026).

Direct Word, Excel, PowerPoint and interactive-page requests now check for a saved result before reporting completion. The full five-scenario Qwen3.5:27b Quick creation/revision journey passes; controlled failures verify inline recovery and preserved drafts. The check covers recognized direct requests, not arbitrary model claims. See [verification](VERIFICATION.md#saved-file-completion-and-live-artifact-workflow--october-14-2026).

Direct memory removal now offers a My memories recovery link, and narrow unresolved references receive immediate clarification without inference. Supported local Quick mode selects exact saved text under a schema; Model default retains its existing selector. Qwen 3.5 27B Quick passes 17 semantic cases and a live Mac chat journey; 9B Model default passes a five-turn phone chat journey. Smaller-model quality and broad interpretation remain limited. See [verification and remaining limits](VERIFICATION.md#grounded-memory-removal-and-direct-recovery--october-14-2026).

Direct forget requests now select saved notes through a bounded host-managed pass, including chat-only models. Simple commands receive an authoritative result from the recorded deletion; unrelated notes and learning-off settings remain intact. No new popup or setup is added. See [direct forgetting](MEMORY.md#direct-forgetting-from-chat) for behavior, model limits and acceptance commands.

Direct “remember this” requests now work with chat-only models while automatic learning is off. Saved notes keep exact source evidence and manual-edit protection; ordinary preferences remain unsaved. The assistant's instructions reflect this host-managed memory behavior. See [explicit memory](MEMORY.md#explicit-saves-with-automatic-learning-off) for limits and verification.

Phone chat controls now have larger touch areas around their compact icons, with room for the moving companion and consistent English/Chinese headers. Edge taps, replies, sending and retained drafts are verified in the browser and native iPhone Simulator. See [phone controls](NAVIGATION.md#easier-phone-controls).

A named saved file can now be opened directly by its exact unique filename. The assistant no longer needs to copy a long internal identifier for that read. Duplicate names require selecting the intended file; wrong names and IDs are never repaired or guessed. This adds no page, popup or setup step.

Personal memory now has a focused model review for direct English/Chinese preference statements, current-source validation, preserved correction identity, and runtime checks for learning-off and explicit forgetting. Ordinary questions skip extra inference; no new setup or popup is added. Phone memory links, source disclosure, editing, correction choices and the learning switch now have 44-pixel touch targets; the empty state stacks its text clearly. Small-model judgment remains limited. See [memory behavior and limits](MEMORY.md).

Saved files and chat attachments now open on a dedicated preview page with Back to chat, All files and browser history. Direct links retain the originating chat, and text previews keep unsaved edits until explicitly saved. See [file navigation](NAVIGATION.md#file-previews-have-their-own-page).

Editable PDF forms now use the details in a normal chat message and return a filled copy, preserving the original. Text, checkbox, radio and list values are supported; missing required fields are reported. See [PDF forms](PDF_FORMS.md) for font/document limits and verification.

A failed reply now offers **Try again** in chat when its saved work can safely resume. It retains the original request, attachments, completed results and unsent draft. See [reply recovery](CHAT_RETRY.md).

When the selected computer is confirmed asleep, **Send** can also continue chat in one action, with an inline explanation that the computer stays asleep. Failed sends retain the draft and owner control. Navigation opens its own page without chat history.

A paused chat can now **Start & resume** its sleeping virtual computer directly. Progress, cancellation and failures stay beside the composer; handback waits for readiness and the original control state. See [computer recovery](COMPUTER.md#resume-directly-from-chat).

## Direct photo and document conversations

Vision models without tool calling can receive attached photos directly through all four model adapters. The normal composer retains drafts, thumbnails and same-chat follow-up context; reply threads include their original attached photos. Setup labels this **Chat, photos & documents**. Image limits, unavailable files and incompatible models are explained before inference; Text, PDF, Word, Excel, PowerPoint and EML files can also be supplied directly to models without tools, with bounded complete extraction, source limits and follow-ups. Apps, computer control and other actions still require tools. See [model setup and photo limits](MODELS.md#photo-chat-without-assistant-actions).

Local-model setup now has a direct **Use a local model** path in AI models. It lists models already running in Ollama or LM Studio on the Relay server, requires explicit activation, reuses an existing matching connection and keeps setup out of chat history. Installed Ollama can be started inline on supported Mac/Linux servers, with cancellation and an explicit saved start-with-Relay choice. Only the process Relay started is stopped on quit. No endpoint/key typing is required at the standard local addresses. See [MODELS.md](MODELS.md) for discovery, recovery and scope.

Your direct messages now get attention while background work waits and resumes automatically. No priority setting or popup is needed. Completed actions are retained. See [direct-message priority](WORK_PRIORITY.md) for behavior and limits.

Send **Stop now** in a direct chat to halt its current and delegated work, pause queued follow-ups, and retain completed results. See [stopping from chat](STOP_WORK.md) for scope and recovery.

Direct-chat follow-ups now update the running request through the normal Send control. Queue follow-up remains explicit and labeled on mobile. Completed tool outcomes, attachments and draft recovery are retained; group-steering limits are documented in [FOLLOW_UPS.md](FOLLOW_UPS.md), and scheduling in [WORK_PRIORITY.md](WORK_PRIORITY.md).

File previews and saved results include **Ask about this**: attach the existing file to the current chat draft in one tap, preserve unfinished text and send only when ready. See [NAVIGATION.md](NAVIGATION.md).

Connected apps now use a separate **Your apps** page with search and a four-service directory. Choose an app by name, or use a custom address/local program; see [APP_DIRECTORY.md](APP_DIRECTORY.md). MCP actions, documents and owner-chosen prompt templates support per-operation permissions, assistant access, inline reviews and durable continuation. Content-only apps work too; see [APP_CONTENT.md](APP_CONTENT.md). See [APP_CONNECTIONS.md](APP_CONNECTIONS.md) for setup, data boundaries and transport limits.

## Incoming mobile shares

iOS has a native share extension for text, links, photos and files. Choose Main or a side chat and Attach; open Relay to find the items above the composer with your unsent draft preserved. Android’s native importer now handles text, photos and multiple files with the same inline destination picker. Its 22 Android framework tests and controlled composer journey pass; an Android application build and OS share-sheet journey remain open. Sending remains explicit. Imports are scoped to the connected workspace and protected against duplicate delivery after a lost acknowledgement or restart. See [mobile sharing](MOBILE_SHARING.md) for behavior, limits, signing and verification boundaries.

## Sample mode

The static preview uses fictional data and deterministic local workflows. It is useful for exercising the UI, real PDF filling, CSV calculations, task state, and review behavior without account access. It is not an open-ended language model. Sample “send” updates the sample Sent folder only.

## Full assistant

Run the supplied Node server and configure a compatible Responses or Chat Completions model endpoint. The model can use the implemented tools. Google OAuth, Brave Search, browser, and Docker capabilities are enabled separately. The server keeps progressing while it runs; stopping the server stops execution. See the [README](../README.md) for configuration.

## Unsupported capabilities

Payment/booking tools, bank connections, built-in Slack/WhatsApp messaging and managed cloud computers are not implemented. Generic Streamable HTTP MCP apps, browser sign-in and programs isolated in Relay’s computer are described in [APP_CONNECTIONS.md](APP_CONNECTIONS.md). Voice calls, assistant groups and bounded workflow teaching are described below. iOS sharing and opt-in native notification implementations are described in MOBILE_SHARING.md and NOTIFICATIONS.md; physical-device push acceptance remains outstanding. The private desktop exchanges files with Relay through an explicit file bridge and has brokered website access without direct guest networking. Existing browser logins cannot be imported from the user's personal browser. Scanned PDF annotation, signatures, XFA forms, and arbitrary font coverage are not implemented. The complete requirement list is maintained in [PRODUCT_PARITY.md](PRODUCT_PARITY.md).

## Pages and messenger behavior

The labeled bottom bar opens Chat, Files, Ideas, Tasks and More. Older saved workspace cards are compact links to their full page; they no longer expand whole forms inside the transcript. The plus button opens the file picker directly in one step. More groups less-used features on a separate page with plain-language descriptions. Changing pages updates the URL, creates no chat messages or model runs, and supports browser Back and reload. The chat remains mounted but hidden and inert, so unsent text and attachments survive a page visit. Pending draft text has a tab-local recovery buffer while its durable workspace save completes. Side chats remain optional; archiving one returns to Main chat.

Incoming and outgoing bubbles group consecutive messages, show tails at the end of a group, and use time separators. Right-click, double-click or choose the ellipsis to reveal actions. Reactions persist locally, and Reply adds a quoted message without replacing the draft. A quoted message links back to its source; the assistant receives that quoted context on send. These are Relay messaging features, not Apple iMessage interoperability. On touch screens, swipe a text bubble right to quote it and focus the composer; a short or cancelled swipe leaves the draft alone. Vertical scrolling, links, code blocks and selection keep their usual behavior. Shared read receipts and other swipe gestures are not implemented. Turn-based live voice calls are described in [voice calls](VOICE_CALLS.md).

## Routines and reminders

Open **More → Routines** or the assistant’s activity view, or type “Show my routines”. A routine can do assistant work or deliver a reminder without a model. Choose once, every day, selected weekdays or an interval of at least five minutes; every schedule stores an explicit IANA time zone and displays its next run.

New routines start paused. Test runs do real work, then the owner can enable, pause, edit, archive or restore the schedule. Instructions are snapshotted for each run; edits affect future runs. Archive cancels its queued/running reply without deleting previous results, tasks or action reviews. The latest twenty run records show their status and output. Results saved quietly can be opened in chat on demand.

Assistant routines use the configured model and normal workspace tools, with the same external-action reviews. Without a model, the labeled sample assistant has its usual limited workflows. Reminders post the supplied text directly and need no model. Results can appear after every run, only when changed, or only on failure; explicit test runs always appear. Change detection compares text and cards, not semantic meaning. The general notification preference controls the in-app notice list. Opt-in native notifications can deliver these updates; provider setup and verification limits are in [NOTIFICATIONS.md](NOTIFICATIONS.md).

The self-hosted worker runs without a browser while its server is running. The static device sample runs only while the app is open. A restart catches up once, without replaying a backlog; overlapping executions of one routine are prevented. Daily/weekly local times follow daylight-saving rules: a nonexistent hour is skipped; a repeated hour runs at its first occurrence only. Routine management tools are unavailable within a scheduled run, preventing recursive schedule creation.

## Incoming-email routines

Choose **When a matching email arrives** in an assistant routine. Set an exact sender address, a subject phrase, or both. Both supplied filters must match, ignoring letter case. A sender alone is allowed; a subject-only rule needs at least three characters. **Test run** lets you select a matching synced inbox email and runs the saved instructions with a source snapshot. Testing does not enable the rule. Without a model, the result explicitly reports a sample match and performs no email action.

Enabling requires a connected Google account. The first successful check establishes a Gmail history baseline; earlier inbox contents are skipped. Subsequent checks run about once a minute while the server runs, using paginated Gmail `messageAdded` history. Sent mail, drafts, spam, trash and messages no longer in the inbox are excluded. This is server polling, not real-time push. General mail sync remains an on-demand bounded view; the event watcher maintains its own durable cursor.

Each accepted event stores the email, instruction version and connected-account generation. History pages and queued runs commit together, so a restart retries only uncommitted work. Changing a rule or enabling it again starts from a fresh baseline. Pause stops new acceptance; already accepted runs remain queued. Archive cancels queued/running replies. Disconnect or reconnect pauses email rules and cancels accepted mail runs, so enabling against another account requires an explicit choice.

A rule accepts at most twenty outstanding runs. A larger burst pauses it and posts a notice to review the remaining inbox mail. Expired Gmail history also pauses visibly rather than replaying old email. Temporary failures retry with backoff, up to fifteen minutes; three consecutive failures pause with a chat notice. Review the account and inbox before enabling again. Existing action reviews continue to protect sending email and changing the calendar. Live-account validation is still outstanding.

## Reusable skills

Standalone `SKILL.md` files can be imported after review and exported as an editable preview. Skills are created/edited directly on the page. File attribution is preserved, shortcuts avoid collisions and imports do not run work or grant tools. Complete skill ZIPs now retain supporting scripts, references, templates, binary assets and license files. The agent reads files on demand and prepares the frozen package in its private computer, then runs helpers with an appropriate interpreter. Imports grant no tools or dependency installation. See [skill files](SKILL_FILES.md).

Open **More → Skills** or assistant details, or type “Show my skills”. Save a method with a name, unique slash shortcut, when to use it and written instructions. Include inputs, steps, checks, result format and approval boundaries. **Save as skill** on an assistant reply opens an editable draft with a link to that source message. Skills can be edited, archived, restored and found in workspace search.

Type `/` in any chat to choose a saved skill; narrow the list by typing, use arrow keys and Enter/Tab to select, or tap a result. Add this run’s details after the shortcut and send. Escape dismisses the picker. **Run skill** in the library accepts optional details and keeps the existing chat draft. Attachments on a slash message are passed to the model by their workspace file IDs.

Each queued invocation stores the method and version used at send time. Later edits and archive do not rewrite that work or its transcript. Assistant routines can also use a skill: they keep a saved version until **Use latest skill version** or a different skill is chosen in the routine editor. Archiving a skill removes it from new selections but does not stop existing routines; pause those separately. Routines can read methods but cannot change skills or create schedules. All external writes still use the existing action reviews.

Custom method execution requires a configured model. Sample mode labels skill runs and exercises only its deterministic built-in workflows. No plugin installation or workflow-recording capability is implied.

## Private desktop computer

The agent can start a real private Linux desktop, run Python/Node, see screenshots, use keyboard and pointer tools, and copy files between the computer and Relay. Opening Computer is a separate page. The owner can take control, which cancels the active computer command and pauses assistant dispatch and queued work until handback. Waiting messages remain in their own bubbles. Completed tool steps use private SQLite checkpoints; uncertain interrupted actions are surfaced for inspection instead of replayed. Named background jobs now return a progress card, retain bounded logs and reconnect across a Relay service restart. Completion queues the frozen original request once; stopping or losing the computer marks them interrupted without replay. Direct Stop job works even during takeover. Interactive PTY jobs accept bounded UTF-8 input, interruption and EOF; lost input acknowledgements can be retried without repeating keystrokes. Controls stay under job details. Agent commands and their detached child apps now freeze in a separate PID/cgroup container. The browser and owner-launched apps remain available; shared X/workspace access still prevents a credential-isolation claim. Commands, files, persistence, isolation and the complete tool loop have real Docker acceptance coverage; the model in that tool-loop test is controlled. A separate public reader remains available. Desktop web connections use expiring owner grants; a grant made during takeover waits for handback before the agent continues. Protected browser writes, credential isolation and live authenticated-account acceptance remain unfinished. See [setup and boundaries](COMPUTER.md), [reference comparison](COMPUTER_RESEARCH.md), and [verification](VERIFICATION.md).

## Saved model connections

Settings includes multiple encrypted model connections, a provider selector, live model discovery, an optional text-generation probe, switching, editing and removal. OpenAI Responses/compatible Chat, Anthropic Messages and Gemini adapters handle text, images and tool calls. Existing runs retain their connection while new requests use the selected model. Local Ollama/LM Studio and custom endpoints are supported. OpenRouter browser sign-in now returns an encrypted server-side key, discovers models and waits for explicit selection/save. Other subscription OAuth and managed-cloud authentication remain open. See [model setup and boundaries](MODELS.md).

Live voice chat starts from the empty composer and uses a compact bar below the chat heading, with setup/recovery text shown only when needed: automatic spoken turns, synthesized replies, interruption, mute, saved transcripts and call-end cleanup. It requires configured chat, transcription and speech services. See [VOICE_CALLS.md](VOICE_CALLS.md) for the pipeline, bounds and verification scope.

Voice services can be connected and tested directly in Settings. Missing listening or speaking opens that page directly from the chat microphone/waveform; once audio is ready, missing AI opens model setup. Completing setup never starts a microphone or call. On a supported Mac server, **Set up voice** installs local listening and selects the installed Mac voice in one explicit action, with the download size shown first. Voice options retains separate providers and Off controls; connected devices use the same server. If a chat model is missing, dictation is available and a Connect AI action opens model settings. Listening accepts an uploaded test recording; speaking offers a playable WAV preview. Saved keys are encrypted on the server, and setup never adds chat messages. Off/on, key clearing, forgetting and environment defaults are supported; active calls block connection edits. See [voice setup](VOICE_CALLS.md) and [Mac system voice](SYSTEM_VOICE.md).

## Optional specialist assistants

Main remains the default in a new window. **Show chats → Manage assistants** opens a separate page for persistent roles. Names, colors, role instructions, style and enabled skills can be edited inline; profiles and draft edits persist. Each assistant has its own home conversation, optional side chats, sourced memories and routines. Hidden assistants keep working. Duplication copies configuration with paused routines and no history or learned memory. See [scope and behavior](ASSISTANTS.md).

Public links have a standalone preview; owner-only links require the server’s access key/session. Recipients can choose **Open in Relay** on the public preview to review the setup in their already connected native app, then **Add assistant**. The selected server and Main draft stay intact; pending imports survive restart without duplicating committed copies. Browser/file import remains available. Imports carry no chats, memories, attachments, account sessions or computer access; every routine starts paused. See [template behavior and limits](ASSISTANT_TEMPLATES.md).

## Assistant appearance

Main and specialists can use the animated anime Sprout, three original shape characters or a cropped picture. The editor previews changes, preserves drafts and saves against the profile revision. PNG/JPEG/WebP inputs become bounded PNG pixels with metadata removed; images follow profile duplicates and version 2 templates. Pause/reduced-motion controls apply, and appearance editing stays off the chat timeline. See [appearance behavior and limits](APPEARANCE.md).

## Specialist handoffs

Ask one assistant to involve another saved role. In a group, text requests, questions and results stay in the shared transcript with clear sender/recipient names. Direct requests and attached files use a specialist side conversation with a progress card in the original chat. Results return automatically. Stop request cancels that request and its descendants while unrelated group work continues. See [handoff behavior and limits](HANDOFFS.md).

## Group chats

Keep Main as your default and add a group from the sidebar when several assistants should help. Select two to six roles, mention a participant or Everyone, or let your model choose who answers. Replies and questions return to their author; drafts, participants and files persist. See [group behavior and limits](GROUPS.md).

## Reply threads

Choose **Reply in thread** from a message’s controls to discuss that result separately. The original message is expandable, reply counts reopen the discussion, and Back to conversation returns to its source. Threads keep their own drafts, attachments and queue, including questions and specialist handoffs. Groups default to the original author and accept explicit mentions. Search includes replies without adding duplicate sidebar chats. See [REPLY_THREADS.md](REPLY_THREADS.md).

## File intake and original bytes

Chat supports file-picker selection, file drops and pasted images, retaining up to eight attachments until Send. Files accepts drops too. Uploads finishing after navigation attach to their original chat. Application uploads allow 8 MiB per file; direct computer transfers allow 8,000,000 bytes. Computer drops and its device picker copy into the current workspace folder while the owner has control, with conflict-safe names. Folders are not accepted.

Large text uploads retain their original binary bytes for download and transfer. The searchable text/preview is bounded at 2,000,000 characters. A shortened preview is labeled and cannot be edited in place; smaller edited text files download their saved edits.

PNG, JPEG, WebP and GIF attachments have visible thumbnails in drafts, share receipts, sent messages and assistant file cards. Draft removal only detaches the file. Image previews keep original download bytes, preserve the chat draft and return keyboard focus. Invalid image content has a readable fallback; SVG/HTML is never embedded as a thumbnail. Blob URLs are revoked when the corresponding view unmounts. Animated GIFs retain their original format; per-image playback controls are not included.

Audio and video attachments now play directly in sent messages and assistant file results, with play/pause, seek and mute controls. Previews preserve the draft and stop on navigation. Configured listening services can transcribe audio through the assistant’s file tool. With current FFmpeg/ffprobe installed on the server, video reads now return metadata, timestamped frame images and selected soundtrack transcripts. The assistant must disclose sampling gaps; continuous video understanding and live-provider quality remain unverified. See [media behavior and limits](MEDIA_FILES.md).

Saved EML emails now show decoded sender/subject/body and enclosed-file controls in the existing preview. Attachments open without adding chat messages and can be read by the assistant through the existing file workflow. Original messages and edited extracted copies remain intact. See [saved email files](EMAIL_FILES.md).

### Wake an existing computer runtime

Docker/Colima must already be installed. See [computer setup and limits](COMPUTER.md).

The owner key stays on the server; setup posts no chat messages. See [device connection and session limits](CONNECTION_RECOVERY.md). The iPhone connection form keeps invalid input with inline guidance. Phone connection/recovery copy supports English and both Chinese variants; browser-blocked ports are rejected before navigation. The Android native recovery controls await SDK build/runtime acceptance.

The opt-in private browser uses a separate bounded container, pipe-only control and brokered HTTPS, preserving the existing inline sign-in/review flow. It shares no workspace, display or direct networking with agent commands. It remains experimental/off pending broader credential/taint and account/device acceptance. See [TRUSTED_BROWSER.md](TRUSTED_BROWSER.md).

Local Ollama setup now supports an explicit inline model download with per-file progress, cancellation and reload recovery. A finished download preselects the model; Use this model activates it separately. No setup chat messages are added. See MODELS.md for boundaries and VERIFICATION.md for completed acceptance.

Text-only models now support ordinary chat through detected Ollama capabilities or saved manual overrides for all four API formats. Unsupported tool/file/image use is explained and never silently discarded. See MODELS.md.

Local Quick models now use constrained memory proposals and exact saved-note references for corrections. This keeps the existing memory link, source quote and editable-note flow, while avoiding missing tool-call results and numbered-target confusion in the tested small models. Simple saved preference statements receive a direct acknowledgment; protected changes retain their existing review, and compound requests continue normally. ## Clear results after tool work
