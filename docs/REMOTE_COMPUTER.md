# A separate computer for a hosted Relay server

Native TLS and runtime acceptance pass on two disposable ARM64 Linux VMs. Public deployment, cloud provisioning and broader device acceptance are separate gates.

Relay's application can connect to a **dedicated Linux VM** with its own Docker engine. The application host needs no Docker socket or host-folder mount. The engine has a pinned CA, verifies a client certificate, and uses an immutable desktop image ID. The ordinary Computer page, guest command runtime, owner takeover, files, restore points and private-browser pipes use the same connection. This is administrator-managed infrastructure; automatic cloud provisioning and certificate renewal are separate work.

The connection file grants control of the dedicated VM's entire Docker engine. It is suitable only for a VM used exclusively as this Relay workspace's computer. Do not point it at the Docker engine hosting Relay, another person's containers, or a machine holding unrelated data. Container restrictions remain enforced by Relay; they are not a substitute for the VM boundary. See [Docker's daemon-access guidance](https://docs.docker.com/engine/security/protect-access/) and [rootless mode](https://docs.docker.com/engine/security/rootless/).

## Prepare a dedicated VM

On a new dedicated Linux VM with Docker, Node and OpenSSL installed, obtain your own Relay source and build its original desktop image:

```sh
docker build -f docker/desktop.Dockerfile -t relay-desktop:local .
docker image inspect relay-desktop:local --format '{{.Id}}'
```

Use that exact `sha256:...` ID and the computer's hostname to create its certificate files. The hostname must resolve from the Relay application server; the server certificate is bound to it. Choose a new absolute directory that stays private to the VM administrator.

```sh
node scripts/create-remote-computer.mjs --hostname computer.example.com --image sha256:REPLACE_WITH_IMAGE_ID --directory /private/relay-computer
```

This command only creates files. It does not change Docker, open a firewall, copy credentials or provision a VM. `daemon.json` is a reviewable configuration for Docker's native mutual TLS listener. On the dedicated VM, merge it with the intended daemon configuration and restart Docker using that VM's service manager. A service unit that supplies `-H` itself must have that conflicting option removed before using `hosts` from the JSON file. Restrict the TLS port to the Relay application server's network. Never enable an unauthenticated TCP listener. Keep the CA and server private keys on this VM.

Copy only `connection.json` to private storage on the application server. It contains the client key, client certificate, pinned CA, endpoint, image ID and persistent workspace ID. Preserve it with your backups. Certificates generated by the helper expire after one year; renewing them requires a deliberate administrator action. Never send the file to a model or place it in source control.

## Connect the application

The Relay process must be able to read the connection file. On Unix it must have no group or world permission bits (mode `0400` or `0600`). Set:

```sh
RELAY_DESKTOP_ENABLED=true
RELAY_REMOTE_COMPUTER_FILE=/run/relay-computer/connection.json
```

Remove `DOCKER_HOST`, `DOCKER_CONTEXT` and `RELAY_DESKTOP_IMAGE` from this process's configuration. The legacy `RELAY_COMPUTER_ENABLED` terminal must remain false. Ambiguous settings fail startup rather than silently selecting a different engine. The supplied Linux image includes the pinned Docker client, with no daemon or host socket.

For Compose, mount this one file read-only in the app service and set the variables above in a private override file. The image runs as UID 1000, so arrange readable ownership without making the file public. Do not mount the application host's Docker socket. Restart the app, open **Computer**, select **Desktop**, then choose **Start computer**. Chat history is unchanged by this navigation and startup.

The connection's workspace ID keeps its remote container and volume names stable across application relocation. A previously unused hosted computer record can adopt it. Existing computer history or owner control prevents an automatic switch; keep that computer's original configuration or use a separate Relay data directory. Removing the file setting is not a migration back to local computer state. Do not attach two live Relay servers to the same connection.

Client certificates are copied into a private temporary directory for the Docker client and removed during graceful server shutdown. No key is placed in command arguments, API state or guest environment. An abrupt process/OS termination can leave that private temporary directory until OS cleanup. Saved files and computer restore points retain their existing policies; generated network grants expire at service restart. The actual VM, engine image and certificate lifecycle remain administrator-managed.

## Verification

Four focused Node tests cover configuration bounds, certificate identity/signature/expiry, file permissions, conflict rejection, temporary-key cleanup and preservation of existing computer history. `computer:remote:test` uses two real disposable Linux VMs and **native dockerd TLS**, with a raw TCP forward preserving TLS from the application container to the computer daemon. It rejects missing/wrong credentials and hostname/CA mismatch; verifies real screenshots, command receipts, agent file export, detached-process freezing, approved/revoked public HTTPS, a separate mount-free private Chromium, restore-point file recovery, MCP stdio discovery/reviewed file writes, and application-container replacement with retained control, messages and draft. The test model is a controlled transport; it does not establish reasoning quality.

The harness requires separate test-owned application and computer engines, the built `relay-server:local`, `relay-https:local` and `relay-desktop:remote-acceptance` images, and a generated connection directory used to configure native TLS on the computer VM. Set `DOCKER_HOST` to the application engine, `RELAY_TEST_GUEST_DOCKER_HOST` to the other engine, `RELAY_TEST_NATIVE_COMPUTER_DIR` to that private directory, and `RELAY_TEST_NATIVE_COMPUTER_PORT` to its loopback-forwarded TLS port. `DOCKER_CONFIG` and `RELAY_TEST_DOCKER` can select private CLI plugins and binary. Never target an existing personal workspace or a shared engine. Each run creates and removes its own application volumes and computer namespace.

Desktop/phone UI and native iPhone acceptance are recorded separately in VERIFICATION.md. Physical phones, Android runtime, Linux AMD64, signed distributions, WAN latency/outages, live-account website compatibility, automatic certificate renewal and migration of an already-used local computer remain open. The computer VM and its persistent volumes need their own backup; the application backup does not include them.
