# Teach by demonstration

Relay can turn a visible workflow on its private computer into a reviewed, reusable skill. This is an original implementation of the interaction described in [Grok Bot’s teaching documentation](https://docs.x.ai/grok-bot/skills-routines-and-automations): demonstrate, review the draft, and test before scheduling. It uses the existing private desktop, skills, model adapters and durable worker.

## Owner flow

In a one-to-one server-backed chat, choose **+ → Teach a task**. The Computer page opens directly to the teaching form; navigation adds no messages, starts no recording and makes no model request. Computer → Teach a task is still available. If the computer is not configured, its setup page opens first. Describe the result, then choose **Take control & record**. Relay starts its computer if necessary and pauses agent control. Perform the browser workflow using the existing pointer, keyboard and text controls. Successful owner interactions queue a screenshot of the resulting screen; **Capture this step** records a settled view after a page finishes loading. This is a sequence of visual steps, not continuous video.

Pause before passwords or private content. Pause adds no new screens or interaction labels. Resume starts from the currently visible screen, so clear private content first. Backgrounding or leaving the page pauses capture; loss of the recording heartbeat pauses it within twenty seconds. The ten-minute wall-clock limit includes pauses. Giving the computer back or stopping it ends recording.

**Stop & review** keeps the review on the Computer page. Inspect the thumbnails or enlarge a selected screenshot inline. Remove anything private before **Create skill draft**. That explicit action sends the retained screenshots and the demonstration goal to the selected model; the model must support images. A connection or response failure keeps the recording and offers a retry.

Edit the draft’s name, shortcut, description and complete method before saving. A saved skill links back to its demonstration. **Give back & test skill** returns control and runs the reviewed skill in its original Main or side chat with the chosen example and original assistant. It performs real work and preserves the unfinished text, attachments, app selections and incoming shares; none of that pending context is included in the test. A newly learned skill is enabled for that assistant when it uses a selected skill list. Changed or unavailable skills, archived chats and reassigned assistants require review before a test can return computer control or queue work. Recordings made before chat binding was introduced retain Main as their destination. Repeated submission returns the same test run. Further tests and scheduling use the existing Skills and Routines pages. Discarding a recording removes its stored screenshots while keeping an already-saved skill.

## What is recorded and shared

Only the virtual computer is captured. There is no microphone, camera or owner-desktop recording. Literal text input, command text and website URLs are omitted from the interaction log. **Visible text can still appear in screenshots**. This is not automatic secret redaction, a credential vault, or an exemption from the computer’s existing browser-isolation limits.

The SQLite `teaching_sessions` and `teaching_frames` tables retain metadata and JPEG bytes. Images are excluded from general workspace snapshots, SSE, chat context and the JSON workspace export. They remain in the server database; a full database backup includes them. Authenticated owner routes serve frames with `Cache-Control: no-store`. Discard removes database rows, not a claim of forensic erasure from backups or SQLite history.

Current limits are twenty recordings, ten minutes per recording, thirty screenshots or 8 MiB of images, and two hundred interaction labels. Repeated identical frames are skipped. Reaching a limit visibly ends capture for review; a longer demonstration needs to be split. Screenshot capture is tied to the active recording generation and computer-control epoch so a late response cannot reappear after pause/resume or handback.

The ordinary agent cannot access these recording tables or request teaching through a model tool. Only an owner-requested draft job receives the retained frames. It has no tools and cannot operate the current computer. This specific analysis of a stopped recording may run while the owner still controls the computer; normal queued assistant/computer work remains paused.

## Draft and test lifecycle

Generation uses one bounded model request with a two-minute timeout. JSON validation checks field sizes, shortcut syntax, and that every proposed step cites an actual retained screenshot ID. It does not prove the model correctly understood a page. The prompt asks for parameterized inputs, visible labels, validation, approval boundaries and uncertainties rather than fixed example values or unsupported claims of success. Successful recorded keyboard navigation is retained alongside the visible labels and focus/result checks, rather than replaced with guessed mouse clicks. The owner reviews the complete method; saving does not enable a routine or certify its quality.

Draft instructions distinguish an app's ordinary **Review/Preview** step from approval for sending, purchasing, deleting or publishing. The assistant should compare a local preview with the supplied inputs itself; creating a local file does not require an invented second confirmation. A visible starting app is a prerequisite to inspect, not a reason to ask the owner to open it again. Saved-skill requests also state their execution intent: a skill supplies instructions to the current tools, rather than an executable that needs separate enabling. File-producing methods require locating and checking the actual app output; a missing download must not be replaced with invented bytes. The file tools explain the separate desktop and command-runner home folders so browser downloads can be found directly. These are model instructions, not a guarantee of semantic correctness or an expansion of tool permissions.

A server restart pauses an active recording. Queued draft requests remain durable; interrupted generation returns to review with an explicit retry. Discarding during generation aborts the request and prevents its response from restoring deleted data. Removing a screenshot invalidates a prior draft. Save and the first test use persisted receipts to avoid duplicate skills/runs after lost responses. The test freezes the saved skill version and retains normal action-review boundaries.

Detected local Ollama models in supported Quick mode receive a JSON schema for the draft, with required step objects, bounded lists/text and screenshot references restricted to retained frames. Other connections keep their existing protocol. Every response still passes the same host validation; a constrained format does not establish that the model understood the recording. Malformed output retains the recording for explicit retry and never creates a skill or executes a tool.

## Verification and remaining work

Seventeen Node cases cover recording privacy, control changes and late frames, heartbeat and duration limits, image bounds, removal, structured draft validation, exactly-once save/test, provider failures, discard races, SQLite reopen, owner-only HTTP access and queued-agent isolation during draft generation. Those cases also cover original-assistant recovery across SQLite reopen, complete pending-context preservation, skill-selection revisions and limits, invalid origins, changed skills and legacy recordings.

The production desktop and phone browser flow uses the actual Docker computer. It starts through the two-item composer menu, checks keyboard/outside dismissal and a real file chooser, and verifies that merely opening teaching starts no work. Separate Main and side-chat drafts and an unsent file remain intact through the final test. It demonstrates a local browser form, pauses across a private input and reload, removes a screenshot, exercises an HTTP vision-provider failure/retry, edits and saves the draft, reopens its demonstration from Skills, and tests through the actual agent worker. The test must produce a real downloaded file with the expected bytes while preserving the chat draft. The model responses are controlled fixtures; they do not establish semantic teaching quality from a hosted model.

The packaged Mac renderer passes the same journey while connected to the actual Docker test server. Electron accessibility checks run in the existing window because its context does not support creating browser tabs. Native iPhone 17 Pro / iOS 26.5 acceptance also passes the complete journey: HTTPS sign-in, native keyboard, composer menu, separate teaching entry, real Docker recording/review, controlled HTTP vision draft, saved-skill test with exact downloaded bytes, original side chat, retained attachment and both drafts, and full relaunch. The Record action is placed immediately below its goal field so recording details do not separate it from the input on a small screen.

Long demonstrations beyond the stated limits, automatic visual redaction, hosted vision-model judgment, physical-device and Android teaching interaction and signed native distribution remain open. See [the verification record](VERIFICATION.md) and [the parity ledger](PRODUCT_PARITY.md).

Run `npm run teaching:test:ui`, `npm run teaching:test:mac` or `npm run teaching:test:ios` with the appropriate Docker endpoint available. Each native acceptance run owns and removes its own Simulator and computer; it does not use the owner’s workspace. The aggregate result is `outputs/relay-evidence/teaching-entry-verification.json` in the task workspace.

`npm run teaching:test:live` exercises an actual local vision model, with `-- --mac` for the packaged Mac renderer. Set `RELAY_COMPUTER_TEST_MODEL`, `RELAY_LOCAL_MODEL_TEST_MODELS` and `RELAY_COMPUTER_TEST_DOCKER_HOST` to installed dedicated test weights and the `relay-live-acceptance` engine; `RELAY_TEST_COMPUTER_IMAGE` can select a prepared compatible image. It records a three-field local browser app, generates and saves the model's unedited method, repeats it with new values, and requires exact downloaded bytes including an app-generated receipt. The test checks actual image transport, computer actions/export, preserved chat draft and reload. A model claim or completed run without the file fails. Detailed successful and failed trials are retained in `../relay-evidence/teaching-live/`.

Actual local Qwen 3.5 27B acceptance now passes the bounded three-field workflow in a browser and the packaged Mac renderer, including new input values, real computer actions and exact app-generated downloaded bytes. Supported Quick-mode drafts use the bounded schema. Earlier failures remain in the evidence: unnecessary setup/review, missing download paths, substituted bytes, malformed output and ambiguous typing. The browser run predates the last input-contract clarification but its valid recorded calls pass the current validator; the Mac run uses the refreshed package/backend. Both preserve the draft and survive reload. The aggregate is `../relay-evidence/teaching-live-verification.json`. These runs take minutes with the local model and do not prove arbitrary workflow fidelity, other providers, physical phones or Android. Generated methods still need owner review.
