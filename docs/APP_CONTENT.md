# App documents and templates

Connected apps can supply documents and prompt templates as well as actions. A content-only app connects through the existing **Your apps** page. Choose its access once, then ask in chat; an `@` app selection can narrow the request. Visiting Your apps or Files does not add chat messages.

In new assistant replies, saved documents read from apps and existing files appear as compact **Sources** links beneath the result. Each opens its normal file page directly. Files produced or delivered by the assistant retain full result cards, even if the assistant subsequently reads them to check its work. Repeated reads produce one link per saved file. This presentation is based on recorded tool operations, not filenames or a model's claims. Older replies without that record keep their existing cards.

Up to eight fixed documents from the selected-app preview also receive direct model tools with empty arguments. Relay binds each name to the selected connection, revision and exact resource entry, so the model need not regenerate those fields. These tools use the ordinary invocation path, including current access, live metadata checks, exact reviews and durable receipts. Changing the selection or connection revision invalidates the old name. Parameterized documents, prompt templates and other tools keep their existing flow; the full ordinary tool catalog remains available. Large catalogs fall back to the existing discovery path.

Document reads follow the existing **Ask each time**, **Allow reads**, or **Blocked** policy. Prompt templates always require an inline choice, even after **Allow all reads**. The card shows the template and supplied fields; **Use template** retrieves it and continues the original request. **Decline** leaves it unused. Drafts and pending choices survive navigation and relaunch. Returned binary documents become saved files with the existing preview and **Ask about this** action.

Template fields are editable directly in that card. Correct a value and choose **Use template**; no follow-up message or separate edit dialog is needed. Unfinished changes stay on this device through navigation, reload and app relaunch. Typing does not contact the connected app or change the saved review. Loading and saving errors offer inline retry, retaining the edited values. Decline leaves the template unused.

The final choice validates the exact current template, connection, assistant access and original request, then records the edited arguments and approval atomically. Repeated submission of the same choice returns its existing status; it never retrieves the template again. Different values cannot replace a choice that another device already approved. The original proposal remains available to durable request recovery, while the ordinary worker retrieves the template with the values the owner chose. This applies to prompt templates; action reviews and resource arguments retain their existing behavior.

For apps advertising MCP completions, each template field offers **Find options** beside its label, keeping the action reachable above the mobile keyboard. Focus and viewport resizing reveal the edited field inside the chat scroller. The note identifies the app that receives the current fields. Typing remains local; only choosing Find options sends a lookup. Choose an inline option to fill the field, or keep your own value. **Use template** remains a separate explicit choice. Cancel, edits, navigation and approval discard an in-flight lookup, and late replies cannot replace newer input. Empty/error states retain manual entry. Options are plain text, with eight shown at a time and a way to show more. Recently looked-up identical fields are cached in memory for 30 seconds; suggestions are not saved in chat, workspace files or the persistent draft.

Discovery records whether an app advertises this capability; existing saved connections need their normal catalog refresh before showing it. A lookup rechecks the live capability, exact template metadata, saved connection and pending review before sending and returning values. It supports HTTP JSON/SSE and isolated stdio apps. The MCP request carries the prompt name, one field/value and other supplied string arguments, including explicit empty values. Replies allow up to 100 values and 128 KB, with the same field length limits; malformed entries fail, duplicates collapse, and options containing known connection credentials are omitted. Limits of 20 lookups per app per minute, two concurrent lookups per app and eight overall bound work. These are query requests; they never call `prompts/get` or approve a review. See the [MCP completion protocol](https://modelcontextprotocol.io/specification/2025-11-25/server/utilities/completion).

## Open documents directly

Choose **Your apps → Documents**, then a document. The searchable list is on its own page; browsing and opening create no chat messages, runs or approval cards. Only documents enabled for the current chat's assistant are offered. Apps without document resources keep their existing controls.

Opening is an explicit one-time owner read, including under **Ask each time**. It does not change the app's standing permissions and cannot invoke tools or prompt templates. A document with fields asks for them in place and reads only when **Open document** is chosen. Fields accept simple text; list/map template arguments remain available through assistant calls. Apps advertising completions offer **Find options** beside each field. Choose an inline option or keep typing your own value; **Open document** remains the separate action that retrieves content. The browser does not automatically refresh the remote catalog.

Find options sends the current text fields only when chosen, using the exact resource URI template, field name and other supplied text as context. Typing, choosing an option and browsing do not read the document, invoke a prompt or create chat history. Empty/error results keep manual entry available. Options are plain text, show eight at a time and can be expanded inline. Editing a field, cancelling, leaving the page or opening the document aborts an unfinished lookup; late results cannot replace newer input. Identical lookups may reuse a 30-second component-local cache. Existing saved connections need a catalog refresh before newly advertised completions appear.

The server rechecks the current chat/assistant, connection revision, enabled resource template and live metadata. Connection or chat changes revoke pending work. Resource options are limited to 2,000 characters each; list/map resource arguments remain valid for reads but are not sent to the text-only completion protocol. Prompt and resource options share the existing per-app/global concurrency and rate limits, bounded responses and configured-credential filtering. HTTP JSON/SSE and isolated stdio use the same validation path. No remote document or standing permission is created by looking up an option.

The returned copy stays in Files. Plain text opens in Relay's existing preview, while binary documents retain their exact bytes and supported previews. Multiple returned parts have an inline selector. **Ask about this** attaches the saved copy to the current chat while keeping its unfinished draft; it does not send a message. Text copies use a safe `.txt` representation, retain their full text within the save limit, and are labelled with the source app. They do not follow embedded resource URIs as host paths or execute app-supplied markup.

Every read rechecks the current chat, assistant scope, connection revision, enabled document, exact arguments and live metadata. Completed retries reuse the same receipt and files. The browser sends an explicit cancellation request as well as aborting its connection when cancelled or left; cancelled or revoked in-flight results are discarded before saving. If a read already finished, cancellation does not remove the completed copy. Owner authentication and same-origin protection cover listing, reading and cancellation. Files are workspace copies, not live subscriptions or edits to the remote original.

## Choose a template directly

Choose **Your apps → Templates**, select a starting point, fill its fields and choose **Use in chat**. Search and field editing stay on the separate page. Apps advertising completions offer the same explicit inline options. Fields and the pending choice survive navigation, reload and native app relaunch on this device. The page names the assistant that will reply; group chats target their displayed first assistant only.

Use in chat retrieves the exact selected template and creates one labelled request with its confirmed contents. It preserves every unfinished composer draft field, including text, files, app selections and shares; those unrelated drafts are not sent with the template. Returned template files are attached to that new request. An existing reply is not silently redirected. No second template approval is needed because the page action is the owner’s exact choice. A configured AI connection is required to use a template; browsing does not need one.

Cancellation and changed chat/assistant/app access prevent late retrieval from queuing work. A retrieval that already completed may retain its returned files. Once the chat request is committed, it uses the existing chat Stop/retry controls. Duplicate submission, a lost response or server restart reuses the completed choice rather than fetching or posting again. A new choice after completion is a new explicit request. Unknown interrupted app outcomes retain the existing no-blind-replay policy.

Templates are source material: their declared roles never become real chat roles or new permission. Generated request labels and template contents cannot teach personal memories. External actions still require the existing reviews. Text-only models can answer already-retrieved text templates; tool/image tasks still depend on actual model abilities. Template context follows questions and existing app/computer continuations without fetching it again. This does not certify semantic quality across all models or third-party templates.

## Protocol and boundaries

Relay supports paginated MCP `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list` and `prompts/get` through Streamable HTTP JSON/SSE and installed stdio programs in the private computer. Discovery does not retrieve a document or apply a template. Apps without a tools capability are supported. Resource/template listing may be absent; invalid metadata, duplicate entries and cyclic pagination fail explicitly.

Content entries use the same connection revision, assistant access, frozen request selection, exact argument validation, encrypted credentials, durable receipts and cancellation checks as app actions. A fresh session rechecks the target metadata before dispatch. Changed metadata requires refreshing and reviewing the connection. Local sessions retain their container isolation and stop during owner takeover; interrupted operations are not replayed under the same receipt.

Resource URIs are opaque app identifiers, including `file:` URIs. Relay sends them to that app's `resources/read`; it never fetches them as a host URL or filesystem path. Template text and declared message roles are source material, not new chat roles, permissions or owner instructions. Known configured credentials are redacted from returned source text. PNG/JPEG/WebP results may also enter image-capable model context; other saved files do not masquerade as images.

URI expansion uses the general-purpose BSD-licensed `url-template` package with independently implemented validation and Unicode code-point prefix handling. Literal paths, reserved expansion, query/list/map expansion and explode modifiers are covered by tests. No competitor application code or artwork is included.

The catalog is bounded to 100 combined operations per app. Templates allow at most 32 fields. Resource replies and prompt replies have at most 32 parts/messages. Existing transport and normalized-result size limits apply; binary blocks are limited to 2.8 million base64 characters and at most eight saved files per result. Long embedded text is returned as a marked excerpt. Files retain their decoded bytes and sanitized display names.

## Remaining scope

Resource subscriptions, push catalog updates, sampling, elicitation, interactive MCP Apps and vendor extensions remain open. Refresh currently updates the catalog explicitly. Physical devices, Android runtime, signed distribution and live third-party account acceptance need separate verification.

Protocol references: [MCP resources](https://modelcontextprotocol.io/specification/2025-11-25/server/resources), [MCP prompts](https://modelcontextprotocol.io/specification/2025-11-25/server/prompts), and [url-template](https://github.com/bramstein/url-template).

## Actual model use and entry discovery

When an app is explicitly selected for a chat request, the model receives up to eight entry names/titles/kinds from each selected app (at most eight apps), labelled as untrusted metadata. This is a bounded view of the existing saved catalog: it reads no remote content, includes no schemas or credentials, and never includes other app revisions or assistants' inaccessible entries. A flag indicates that more entries are available. Static documents include host-defined `arguments: {}` because those reads accept no input fields. The model can call those exact entries directly, and may request independent reads together. This preview does not fetch document contents. Parameterized documents, tools and prompt templates still obtain their input schema from `list_app_tools`. For selected catalogs with at most 64 distinct entry names, the existing model tool definitions also include those exact names and connection IDs as bounded choices. Larger catalogs keep normal discovery. This is a model hint, not an authorization boundary: actual calls retain live metadata, revision, field and permission checks. Global tool definitions are never mutated. Already chosen template contents do not get this extra catalog preview.

The assistant is instructed to read app documents through their app rather than search for them as local Relay Files. An unknown exact tool name now explains how to list real entries; it no longer looks like an app with no operations. Document titles and combined names are not silently translated into actions. This addresses two failures observed with a real 9B model, without adding owner steps or weakening permissions. A confirmed metadata change before dispatch now returns a specific Refresh instruction instead of the generic connection error; this fixed host message contains no app-provided error text or credentials. No read/action is sent when that definition check fails.

`npm run apps:content:test:live` uses an actual installed local model, the production provider/worker, a phone browser and an independent JSON/SSE MCP app. Add `-- --mac` for the packaged Mac client. Set `RELAY_APPS_TEST_MODEL`, an independent `RELAY_LOCAL_MODEL_TEST_MODELS` cache and optionally `RELAY_EVIDENCE_DIR`. It uses acceptance port 41334, refuses an occupied port, downloads no weights and leaves owner model configuration alone.

The six cases combine text and a binary CSV into an answer with an unpredictable meeting code, expand a dated/tagged resource with an unpredictable room, ignore hostile source instructions, reject changed remote metadata before reading, explain an unavailable read without inventing the code, and use an explicitly selected template once while preserving the Main draft through reload. Captured requests/replies, protocol traffic and screenshots accompany each receipt. These are actual model decisions against synthetic app data, not live vendor accounts or certification of every model's task quality. The initial exact-name and app/file-confusion failures remain in the evidence. A repeat 9B trial also copied the wrong resource identifier and stopped at a statement of intent; the bounded name choices were added after that failure. Model reliability remains limited even when a later journey passes. A later harness checked the prior completed run before the template request was queued; it now waits for the new run before checking completion.

Final receipts are indexed in `../relay-evidence/app-content-live-verification.json`. Earlier failures are diagnostic evidence, not passes. Android and physical-device runtime, live accounts and the other protocol capabilities listed above remain open.

Supported UTF-8 text files returned as binary resources now include a small `textPreview` in the same tool result. Plain text, CSV, TSV and JSON are supported; invalid UTF-8, control-bearing data and other media retain file-only handling. Previews are limited to 2,000 Unicode code points and flag truncation, so larger content still needs `read_file`. Known connection credentials are redacted before clipping. This is source data, not an executable document or permission. Original stored/downloaded bytes remain unchanged. It removes an extra model read for small app documents; the model must still reason correctly over the actual contents. A 9B trial that retrieved a CSV but guessed a formula without reading it motivated this change; that failure is retained.

## Automatic document-read recovery

HTTP `resources/read` requests, including expanded resource templates, get at most one automatic retry for a recognized network disconnect or HTTP 502/503/504. A partially received JSON or SSE response is discarded; the failed session closes before a fresh session starts. Both attempts share the original timeout budget and operation receipt. Each attempt rechecks current access, selected-request guards, the saved connection revision, exact arguments and live metadata. A successful retry saves only one result. Cancellation, revocation, changed metadata, authentication failures, malformed protocol data and size-limit failures do not trigger retry. Generic app tools (even tools annotated read-only), prompt retrieval and isolated stdio programs retain their existing no-replay behavior.

A persistent transient failure records an unavailable receipt. Reusing that operation after restart does not contact the app again; a later new owner request can try again. The model receives a fixed `document_unavailable` code and is instructed to describe the missing source without guessing or suggesting reconnection without evidence. No retry button, popup or extra owner step is added. Executing receipts left by an interrupted server still cannot be blindly replayed.

Agent calls to parameterized documents must supply nonempty path-selection fields. Omitting a date or name returns a schema-recovery instruction before any read; optional query and fragment expansions remain optional. This check applies to agent invocation, while explicit owner document forms retain the existing RFC 6570 behavior and saved schema fingerprints. It prevents a model from silently reading a default path after the owner asked for a dated document. The live fixture returns its unpredictable room only for the exact requested date and tag, so a plausible answer from a different path cannot pass acceptance.
