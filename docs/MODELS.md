# Model connections

## Everyday replies

Relay's conversational default asks for a direct answer, usually one to three short sentences for an everyday request, without a routine closing question or offer. Explicit language/format requests and the detail needed for complex work take precedence. This applies to action-capable and chat-only connections; it does not remove tools, truncate generated text or change provider sampling/reply mode. Model compliance still varies.

The live conversation check supports `--main-chat`: seven continuous English/Chinese requests and follow-ups, an exact plain-text file request, then file recall in a new side chat. It verifies requested shape, no unwanted questions or saved objects, and draft recovery. Its receipt records first stored partial text separately from completed-reply time. Inspect actual wording as well: automated format checks cannot establish natural language quality or factual personalization. See [verification](VERIFICATION.md#everyday-chat-and-continuous-conversation-acceptance--october-14-2026).

Chat-only connections can select saved notes for direct forgetting through bounded JSON. Relay owns deletion, stale-state checks and simple-command acknowledgments; this grants no browser, computer or app actions. A semantic no-match remains possible and leaves notes intact. See [memory behavior](MEMORY.md#direct-forgetting-from-chat).

Compatible Chat Completions adapters preserve both `reasoning` (including Ollama) and `reasoning_content` under their original keys between tool rounds on the same connection. Neither becomes visible chat text. Streaming and JSON responses enforce the same reasoning size/type limits; switching providers or connection revisions strips private provider state. A reasoning-only response is not a final answer. See the dated verification record for actual local-model trials and their limits.

## Start from your chat

Before an AI model is connected, **Connect AI** is the main action in an empty conversation. Fictional examples stay under **Try a sample first**; a conversation with sample messages shows a compact connection reminder above the composer. Static demo mode keeps its existing sample experience.

Connect AI opens the separate AI models page. Cancel returns to the retained draft. After explicitly saving/using a model or choosing a saved connection, Relay returns to the original Main or side chat with its draft and attachments. Nothing sends automatically. With one running local model, the path is **Connect AI → Use a local model → Use this model**. On an empty local setup, **Set up & use** handles installation, startup, the displayed model download and activation in one action; see LOCAL_MODEL_INSTALLATION.md. Multiple existing models still need selection, and provider sign-in or credentials follow the existing flows.

The return destination is local to this navigation flow and survives a page reload. Ordinary Settings visits stay in Settings. Turning AI off, a passive configuration refresh, failed activation or an activation response arriving after the user leaves setup cannot force a return to chat. A deleted originating chat falls back to Main. Full app relaunch retains the underlying draft; it does not promise restoration of every unfinished setup screen.

Open **Settings → AI models**. **Connect OpenRouter** offers browser sign-in followed by model selection. **Use a local model** finds models in Ollama or LM Studio on your Relay computer, without entering an address or key. If installed Ollama is stopped, choose **Start Ollama** directly in this page. For an API key or custom server, choose **Add a model**. Choose a provider, enter its API key, then use **Find models** or type an exact model ID. **Save & use model** selects it for new requests. The optional **Test connection** inside **Connection details** sends only a short text-generation probe, which may incur a provider charge. Setup, testing and switching do not create chat messages.

## Sign in with OpenRouter

The first setup screen offers **Connect OpenRouter**, **Use a local model** and **Add a model**. Choose **Connect OpenRouter** for browser sign-in. Your browser opens the official provider sign-in page; return to Relay afterward, choose from its model list and select **Save & use model**. There is no API key to copy. The provider controls authorization, account limits and charges. Opening Settings makes no provider request, and sign-in alone neither activates a model nor sends chat context. The existing provider/key and local-model forms remain available through **Add a model**.

Relay exchanges the single-use authorization code on its server using S256 PKCE. A one-use opening ticket binds the callback to that browser through a scoped HttpOnly cookie; it does not share the Relay owner session with the external browser. Keys and pending credentials use the encrypted model vault, never browser storage, chat, workspace exports or public connection responses. Only the opaque pending request ID is kept in session storage for reload recovery. The returned key can only be used with the official OpenRouter endpoint and Chat Completions format.

Sign-in expires after ten minutes and supports at most four unfinished requests. Cancel discards the pending local credentials; it cannot revoke a key already created in the provider account. Remove or revoke unwanted keys in OpenRouter’s account settings. A restart preserves a completed authorization awaiting model selection, but an interrupted code exchange requires a fresh sign-in rather than replaying a possibly consumed code. Saving the key and its completion receipt is one SQLite transaction. Retrying a save returns the same connection and preserves any newer active-model selection.

Decline, expiry, rejected codes and connection errors stay inline. An unavailable model catalog leaves a manual model-ID field and an explicit retry. A blocked browser window offers **Open sign-in**. A declined response without a state parameter is accepted only as failure, using the opaque callback flow ID and its initiating browser cookie. Authorized responses still require the full state and PKCE checks. Desktop and mobile apps open the system browser using the same bounded sign-in link. No account login, payment, or live-provider quality is certified by the controlled test fixture.

This is independently authored against the [OpenRouter PKCE documentation](https://openrouter.ai/docs/guides/overview/auth/oauth), following the account-then-model setup distinction observed in Hermes. It does not import another assistant’s accounts, secrets or code. Public HTTPS Relay deployments must set `RELAY_PUBLIC_URL` to the address their phone/browser can reach; loopback callbacks support local desktop development. The mobile app still needs its existing Relay server connection.

After discovery, a single model list replaces the manual field. **Enter a model ID instead** switches back without losing the selection. Changing a key, endpoint or API format clears the old discovery list. A rejected provider key stays as an inline form error; it does not sign the owner out of Relay.

Relay implements its own adapters for OpenAI Responses, OpenAI-compatible Chat Completions, Anthropic Messages and Google Gemini generateContent. Presets cover OpenAI, Anthropic, Gemini, OpenRouter, xAI, DeepSeek, Groq, Mistral, Together AI, Ollama and LM Studio. **Custom endpoint** accepts other services implementing one of these four formats. Model lists come from the configured service; manual IDs remain possible when listing is unavailable or paginated. A listed model is not a guarantee of tool, image or account access.

Use a chat model with function calling for assistant actions, and vision for computer screenshots. The same active connection powers chat and the agent loop, including memory and computer tools. Test connection verifies text generation only. Audio transcription and speech retain their own service configuration.

## Model abilities and chat-only models

Local setup and the active connection show whether the selected model reports tool and image support. An Ollama model without tools can now hold an ordinary conversation without the tool definitions that previously caused HTTP 400. It uses a shorter conversational prompt and cannot dispatch tool calls. Photos can be supplied directly as described below. Text, PDF and Office documents can also be supplied directly. Requests with selected skills or selected apps receive an explicit explanation that they need a model with tools; unsupported image observations fail before inference, without discarding the image. There is no automatic retry on a capability error or silent switch to another provider.

For another provider, edit the connection and expand **Connection details**. **Assistant actions → Not supported · chat only** disables tools; **Image support → Not supported** prevents unsupported image requests. Automatic is the default. Supported is an explicit owner override when the provider is known to support the feature. These settings are saved with the connection revision, frozen for in-progress requests and reset to Automatic when the endpoint, API format or model changes in the editor. They apply to all four implemented API formats. Environment-only connections remain read-only; use a saved connection for manual overrides.

Automatic detection queries only `http://127.0.0.1:11434/api/show` for the selected Ollama model, with redirects disabled, a three-second deadline and a bounded response. It sends the model name and that connection's key if configured, never conversation content. It does not guess native API paths on other services or scan addresses. Valid metadata is cached in memory for five minutes by endpoint/model/key; unavailable or malformed metadata remains unknown for fifteen seconds. Unknown capabilities retain existing protocol behavior, so choose a manual override when a provider does not report abilities. Metadata does not prove model quality or grant permissions.

A text-only fallback preserves completed tool results as explicitly untrusted conversation text, discarding incompatible tool-message roles and opaque provider state. It cannot replay or invent an actionable tool call. Prior messages and personal notes remain available as context; this does not grant file/app/computer access or memory writes. Audio still uses its separate configured services. Vision models without tool calling can now receive explicitly attached photos directly; other file formats still use tool-capable intake.

The [official Ollama model-details API](https://docs.ollama.com/api-reference/show-model-details) and [tool-calling documentation](https://docs.ollama.com/capabilities/tool-calling) informed this original implementation. The earlier SmolLM2 download now reaches a live greeting reply without HTTP 400, but the same 135M model gave a poor arithmetic answer and drifted from Relay's name. Those quality limitations remain explicit; do not use the small compatibility probe as a recommended assistant model. See VERIFICATION.md for actual acceptance scope.

## Photo chat without assistant actions

A model with image support can answer about attached photos even when it has no tools. Setup shows **Chat, photos & documents**. Drop, paste or choose photos in the normal composer, then send your question. There is no additional mode or confirmation. Photo drafts and existing conversations keep the same persistence and preview controls.

For a connection whose tool capability is explicitly false, Relay supplies inline PNG, JPEG, WebP or GIF bytes directly through the existing protocol adapter. An explicit **Assistant actions → Not supported · chat only** override uses the same path. Ordinary tool-capable models retain their `read_file` workflow. The compact prompt permits discussing supplied pictures but does not claim access to other files, apps, computer controls or memory writes. Photo content is untrusted source data, never instructions or action approval.

Follow-up questions can reuse photos from the current conversation's last forty messages, including after a server or app restart. Reply threads include their original message's attachments; unrelated chats and workspace files are not scanned. Duplicate attachment references are supplied only once, at their most recent reference; an identical photo already present in a prior tool observation is reused. Current-request photos take priority within eight images and 12,000,000 total encoded image characters per inference request; each image must be no larger than 8 MiB. A current attachment that is unavailable, unsupported or exceeds the budget fails clearly before inference. Older images that are unavailable, incompatible or beyond this budget get an explicit context notice rather than an invented visual description; reattach them when needed. Switching to a text-only model therefore permits ordinary conversation without silently claiming to see old photos.

Original bytes remain in Files. Derived image messages are constructed synchronously after capability lookup and the control/cancellation check, sent only to the selected or explicitly approved backup connection, and not copied into durable agent checkpoints. Incompatible backups cannot silently drop a current photo. Actual provider image formats, image counts, animated-image interpretation and visual reasoning quality still vary. Audio and video intake remain a tool-capable workflow. Text, PDF, Office and saved EML email can use the direct document path below.

`photos:test:direct-ui`, `photos:test:direct-mac` and `photos:test:direct-ios` use the actual Relay worker with an independent HTTP vision-only provider. The opt-in `photos:test:direct-live` requires `RELAY_PHOTO_TEST_MODEL` and `RELAY_LOCAL_MODEL_TEST_MODELS`; it starts an installed model on an isolated test port and downloads no weights. The corresponding `photos:test:direct-local-mac` runs the same real-model photo task through the packaged Mac app’s own backend, then quits and relaunches it. See VERIFICATION.md for completed runs and limits.

## Document chat without assistant actions

Attach a text, PDF, DOCX, XLSX, PPTX or saved EML email in the usual composer and ask a question. **Ask about this** from a saved file preview uses the same path. A model without tools receives the extracted contents directly; no new mode or approval popup is added. Setup labels this **Chat & documents**, or **Chat, photos & documents** for a model with vision.

Relay supplies only explicitly attached files from the current conversation's last forty messages, current request and original reply-thread context. Current attachments take priority; duplicate references are supplied once at their most recent reference. Follow-ups retain those references through server or app restart. Unrelated chats and unselected files are never searched. Extraction does not change original bytes or save a memory. Derived text/images are prepared at dispatch time and are not written into agent checkpoints.

The direct path allows up to eight documents, 8 MiB per file and 60,000 extracted text characters in total per inference. PDF and Office readers consume every text chunk with a stable content hash. UTF-8 text uses the original bytes, not the shortened preview. Missing, malformed, incomplete or over-budget current files stop before inference with a next step. Unreadable or over-budget historical files have an explicit omission notice, so an ordinary new question can proceed. A suitable tool model can read larger sources in parts. Cancellation, worker ownership and computer handback are rechecked after asynchronous parsing; changed or deleted sources cannot be dispatched as current files.

PDFs include complete extracted text and form metadata within the PDF reader's limits. With vision available, PDFs of up to eight pages also include every page image. For longer PDFs, only pages without extractable text receive images; more than eight such pages requires a smaller section. With vision explicitly disabled, a PDF containing a page without text requests a vision model or text copy. Unrendered pages are identified as text-only: diagrams and layout are not claimed as inspected. All PDF page images, photos and earlier image observations share the eight-image/12,000,000-encoded-character budget. Office extraction retains the parser's limitations for images, charts, layout, tracked changes and saved formula values. Saved email headers/body are unverified source material; enclosed attachments are listed, not opened automatically. No links, scripts or macros are run.

`files:test:direct-ui`, `files:test:direct-mac` and `files:test:direct-ios` exercise the real worker with a controlled HTTP model. Opt-in `files:test:direct-live` and `files:test:direct-local-mac` require `RELAY_DOCUMENT_TEST_MODEL` and `RELAY_LOCAL_MODEL_TEST_MODELS`, use an existing model cache and never download weights. See VERIFICATION.md for actual completed runs and remaining device/model limits.

## Local and custom services

Choose **Use a local model** to check the standard Ollama and LM Studio services on the Relay server computer. With one available model, review the preselected choice and press **Use this model**. With several, choose one first. An existing matching saved connection is reused; reconnecting does not create duplicates or overwrite its credentials. Discovery never changes the active connection or sends a prompt. Model listings do not guarantee tool or image capability.

Discovery runs only after this explicit action. The owner-only server endpoint makes credential-free GET requests to `127.0.0.1:11434/v1/models` and `127.0.0.1:1234/v1/models`, disables redirects, bounds each service to three seconds and retains successful results when the other service is unavailable. It does not scan other ports, install software, start services or download model weights. Cancel or leaving setup aborts the request; late responses cannot reopen the picker. Settings and chat history stay separate.

If nothing is available on a supported Mac server, the inline state offers **Install Ollama** with progress, cancellation and retry. Other servers explain how to open a local service and load a chat model, with **Check again** and **Enter connection details**. A running service with no listed models is identified separately. Custom addresses, key-protected local endpoints and manual IDs use the existing form. On a phone, “local” always refers to the Relay server, not the phone. The new picker requires an updated Relay server.

Ollama defaults to `http://127.0.0.1:11434/v1`; LM Studio to `http://127.0.0.1:1234/v1`. Install the local runtime from this page on supported Mac servers, or separately on other platforms. See [local installation](LOCAL_MODEL_INSTALLATION.md). A running Ollama with no models now offers an inline model download. Relay can start an installed Ollama on supported Mac/Linux servers; LM Studio and other services are opened separately. Localhost refers to **the Relay server computer**, even when you use Relay on a phone. Remote endpoints require HTTPS; loopback development endpoints may use HTTP. The endpoint is an API base URL, without `/chat/completions`, URL credentials, a query string or fragment. Select the API format in Connection details. This is an owner-controlled connection setting; the model cannot change it.

### Download a local model

An empty Ollama now offers **Download · about 4 GB** for Qwen 3.5 4B, with its model/license page beside it. **Choose another Ollama model** accepts an explicit official-library model tag, including a publisher namespace. Custom model sizes and capabilities vary. The suggested model supports tools and images; listing or downloading any other model does not establish assistant-tool compatibility. Sizes are approximate and mutable registry tags can change.

Downloads begin only from the explicit button. The Relay server asks its fixed loopback Ollama API to pull the chosen model; on a phone, the files still go to the Relay computer. No registry URL, arbitrary host/path, credential or insecure-transfer setting can be supplied. Recognized cloud tags are rejected. Downloads use Ollama's normal model storage or the operator's existing `OLLAMA_MODELS` directory. Relay does not install Ollama or include model weights in its app packages.

Progress names the current model file and its reported byte count, rather than pretending each layer's percentage is an overall percentage. Leaving Settings or reloading keeps the request running; reopening setup restores its progress. **Cancel download** cancels Relay's HTTP request. Ollama may retain partial files or continue a transfer shared with another client. Relay never deletes a shared cache or stops an independently running Ollama service. Another explicit Download retries; there is no automatic restart after Relay exits or crashes. Startup/running records persist privately so an interrupted download stays visible after reconnecting.

Only one Relay download runs at a time. Opaque request IDs deduplicate retries and prevent a stale Cancel from cancelling another request. A two-hour overall deadline, two-minute stream inactivity deadline, 64 KiB progress-line limit and 2 MiB catalog limit bound requests. Progress events are consumed and discarded; their cumulative byte count does not stop a large download. Provider response bodies are not echoed into errors. Success requires both Ollama's completion event and the exact requested model in its installed catalog.

After success, setup refreshes the local list and preselects the downloaded model. **Use this model** remains an explicit separate action; neither download nor status polling activates a model, sends inference, nor adds chat messages. A download can still fail because of disk space, network access, missing tags or Ollama version. Installation, arbitrary custom registries and native Windows runtime management remain outside this flow.

This is independently authored against the [Ollama pull API](https://docs.ollama.com/api/pull) and [official Qwen 3.5 4B listing](https://ollama.com/library/qwen3.5:4b), checked October 13, 2026. `models:download:test:ui`, `models:download:test:mac` and `models:download:test:ios` use a separate streaming HTTP fixture. The opt-in `models:download:test:live` requires `RELAY_ALLOW_MODEL_DOWNLOAD=true`, `RELAY_DOWNLOAD_TEST_MODEL` and an isolated `RELAY_LOCAL_MODEL_TEST_MODELS` cache; it downloads actual weights and may use substantial bandwidth/disk space. Completed acceptance and its scope are in VERIFICATION.md.

### Start installed Ollama

When Ollama is installed but stopped, **Use a local model → Start Ollama → Use this model** gets to chat without a terminal. Startup progress, cancellation and errors remain inline. **Start Ollama with Relay** is offered before the first start and saved only after successful startup; no automatic startup is enabled merely by opening setup. After startup, this option lives in the collapsed **Startup options** section. Turning it off affects the next Relay launch and leaves current work running. Discovery and startup never activate a model or add messages.

Relay starts only a detected installed executable with the fixed `serve` argument, listening on `127.0.0.1:11434`, with Ollama cloud disabled and model pruning disabled. It downloads no software or weights. Existing models remain in Ollama's normal storage, or the operator's `OLLAMA_MODELS` directory. Only a small allowlist of environment values is forwarded. Mac application/Homebrew locations and standard Linux executable locations are detected; Windows startup is unavailable. Other addresses and runtimes use the existing manual connection form.

A private process supervisor drains the Ollama instance and its model runners when Relay quits, even if Relay's parent process crashes. It also handles a leader exiting before its descendants. An Ollama service already running outside Relay is used without adopting or stopping it; an occupied port belonging to another service stays an inline error. Startup has a twenty-second deadline. Cancelling an unfinished start cleans up its process and saves no new preference. No host login item, shell profile or machine-wide service is changed. The startup choice is private server state; it is absent from chat and workspace exports.

On a connected phone, startup runs on the Relay computer. The desktop package owns its backend, so quitting it stops its owned local model service. A separately hosted Relay server keeps serving devices until that server stops. Real process and inference acceptance on Mac is recorded in VERIFICATION.md; Linux runtime startup, Windows startup and physical mobile devices are not certified.

The protocol adapters handle text, inline images and tool calls. Responses retains encrypted reasoning items; compatible Chat retains provider reasoning fields; Anthropic retains signed thinking and tool blocks; Gemini retains thought signatures and function IDs through tool results. Proprietary extensions and every model family have not been individually certified. AWS Bedrock signing, Vertex service-account auth, Azure-specific paths, other provider subscription logins, automatic account import and key rotation are not implemented. A paid chatbot subscription is not automatically an API connection.

## Persistence and switching

Multiple named connections are saved. Selecting a connection changes future work; each started request records its connection and revision, keeping that choice across worker retries and server restart. Credentials for a connection with unfinished work cannot be edited or removed. Switching to another saved connection remains available. A resumed request whose frozen configuration is gone fails explicitly instead of sending its context to an unapproved provider. Automatic fallback is off unless the owner configures the backup list below.

Edit a saved connection to change its model or key. A blank key retains the saved key for the same destination and API format. Changing endpoint, provider preset or format clears that reuse. Removing a connection clears its active selection and saved credentials; it does not erase chats. Choosing **No AI model** keeps saved connections and returns to Relay’s explicitly labeled sample workflows.

Environment settings remain supported as a read-only **Server environment** connection: `RELAY_MODEL_BASE_URL`, `RELAY_MODEL_ID`, `RELAY_MODEL_API_KEY`, `RELAY_MODEL_PROTOCOL`. Protocol values are `responses`, `chat`, `anthropic` and `gemini`.

**Settings → Usage** shows persisted request counts and reported tokens across saved connections, including labeled connection checks and separate backup attempts. ## Optional backup models

With at least two saved connections, expand **Backup models** beneath the active connection. Add up to three saved models and arrange their order. The list belongs to the selected primary connection. The disclosure explains that each backup can receive the same chat, files and tool results, with its own provider charges. No backups are selected automatically. **Turn off backups** clears that primary's list for new requests.

Each new request starts on the selected primary and freezes its approved backup IDs and revisions. If the provider is unavailable before showing any reply text, Relay tries the next saved backup. Once selected, that backup continues the unfinished request, including across a server restart. Completed tools are not replayed. Editing a policy affects future requests; connections frozen by unfinished work remain protected from editing/removal. Global model selection stays unchanged, so the next new request starts on the primary again.

Eligible failures are network interruption, provider timeout, HTTP 401/402/408/429 and 5xx, plus recognized structured authentication, quota, overload and service failures. Refusals, content filters, malformed output, output limits, local errors and cancellation never trigger a backup. Relay does not replace a partially displayed reply. Each model completion has a shared 180-second deadline; there is no account rotation, persistent cooldown or background retry loop. Tests and discovery call only their chosen connection.

Every attempt respects owner computer takeover and cancellation. After handback, stale screen observations are invalidated before a backup receives context. Text, tool results and canonical images remain available, but opaque reasoning/signatures are replayed only to the same connection and revision. Each destination receives only its own saved key. A completed reply carries a small **Answered with … · backup model** label, without adding a separate history entry.

## Credential boundary

The server stores the connection vault using AES-256-GCM in its private SQLite secrets table. It creates `model-vault.key` with mode `0600` in the data directory. Back up the database and key together with Relay stopped. The key is separate from the database but on the same computer; this does not protect against a compromised server account or a backup containing both files.

API keys are write-only in the UI and absent from workspace state, chat, SSE and exports. Owner authentication, host validation and same-origin write checks apply to model APIs. HTTP redirects are disabled so credentials are not forwarded to a different endpoint. Network, malformed-response and provider errors use bounded generic messages rather than echoing response bodies or keys. The selected provider receives the agent’s chat context, saved memories and tool results when work runs, as described beside the connection form.

## Research and verification

### Real local-model acceptance

On October 12, 2026, Relay passed opt-in inference with Ollama 0.40.3 and `qwen3.5:4b` on this arm64 Mac. A fresh fictional workspace discovered and saved the model, saved a hotel preference through an actual tool call and recalled it in a new side chat, identified an original image's shape/color/code, and created a downloadable text file. With a real isolated Linux desktop, the model read an unpredictable caption from screen pixels, ran Python to write it into a file, and exported independently verified bytes. Phone-browser chat synchronized the real answer to the desktop without replacing its unfinished draft.

The test exposed an actual file-format mismatch: the model created `weekend-plan.txt.docx` while claiming to create `weekend-plan.txt`. The text tool now preserves `.txt` and exact UTF-8 bytes, keeps `.md` support, rejects oversized input instead of truncating it, and returns the saved name/type/size. Office creation also returns the actual name and type. Tool instructions direct plain-text requests to the text tool. This reduces the mismatch; it does not guarantee arbitrary model behavior.

Run against an already running local service and installed model:

```sh
RELAY_LIVE_MODEL_URL=http://127.0.0.1:11434/v1 \
RELAY_LIVE_MODEL_ID=qwen3.5:4b npm run models:test:live
```

These opt-in tests require installed Chrome (browser journey) or the Mac package; they are separate from deterministic `npm test`.

## Quick replies on local Ollama

New connections to the standard local Ollama chat endpoint start with **Quick replies**. In the existing connection details, **Reply style → Model default** restores the model's usual reasoning. Existing saved connections without a reply style keep their previous provider defaults. Editing a connection is still blocked while it has unfinished work; its revision pins the mode along with the model and credentials.

Quick replies sends `reasoning_effort: "none"` only when Ollama's bounded `/api/show` metadata explicitly advertises `false` as a supported thinking value. A missing or malformed value, named-only levels, a different endpoint or another API format receives no guessed override. Model changes reset the draft setting; hosted connections never receive this Ollama-specific control. The 5,000-token response limit and action tools remain intact. No automatic retry or partial tool execution is introduced when a response reaches its limit. An unfinished local default-mode response suggests Quick replies only when the model advertises support.

Quick local requests also use the compact capability catalog already used for voice: common conversation, saved-data lookups, file and selected-app tools are ready immediately; every other available tool keeps its exact name in a grouped capability directory and loads its full schema on demand. Explicit plain-text file and saved-note requests preload their writing schema, including after a bound clarification answer; other requests keep writing in discovery. This selects instructions only and does not execute a file operation. Explicit document, reminder and email-review requests retain their existing schema hints. Source grounding, honest completion and exact-action reviews remain authoritative. The catalog decision and loaded definitions survive restart and backup-model selection. Older unfinished typed requests retain their original full schemas. Other model settings keep the complete typed tool definitions. This is internal discovery, with no extra owner control.

For explicit plain-text file requests, Relay checks for a real file with host-created, request-bound provenance and a matching filename/type/content fingerprint. Verified computer exports and completed, bound specialist results can also satisfy delivery. An old upload or an assistant's prose cannot. Unsupported completion text stays out of chat and speech while one repair is attempted; another unsupported claim fails explicitly. The checkpoint retains successful writes and the repair budget. This proves saved presence and provenance; requested contents still require semantic or exact-byte acceptance. General notes can still use other document formats, and ordinary inline writing is unchanged.

Direct requests to save a reusable skill also require a real saved method tied to the current request and its intact version/content fingerprint. Unsupported completion text stays hidden while one repair loads the deferred schema and saves the method; repeated failure is explicit. The method is not executed by saving it. This guard does not preload the skill schema, change version checks or add an owner interaction.

The primary references are [Ollama's thinking metadata](https://docs.ollama.com/capabilities/thinking) and its [chat compatibility controls](https://docs.ollama.com/api/openai-compatibility). This is a response-speed choice, not a guarantee of reasoning quality; choose Model default for tasks where its longer reasoning helps.

## Conversation and named-file acceptance

Assistant guidance distinguishes an ordinary conversational answer from a requested saved output. General suggestions and drafts should stay in the chat, while file requests still use the existing tools. This is model guidance, not a hard restriction on actions or a guarantee of a model's judgment.

The `read_file` tool accepts either an exact unique `name` or an exact `id`, returning the canonical `fileId` for later page/form/video tools. It never normalizes names, repairs IDs, searches the host filesystem or chooses the first duplicate. Existing readers, limits and source-data handling remain in place. A missing or duplicated name directs the model to `list_files`; asking the owner is necessary only when the intended file still cannot be determined from the request and context.

`RELAY_CONVERSATION_TEST_MODEL=qwen3.5:9b RELAY_LOCAL_MODEL_TEST_MODELS=/path/to/dedicated/cache npm run chat:test:intent-live` exercises five actual-model cases through a phone composer: an ordinary suggestion, a two-sentence explanation, a short Chinese draft, an exact downloadable text file and reading that file from a new side chat. It checks unexpected file/task/goal/routine mutations and clarification cards, records replies and transport, and preserves an unsent draft through reload. It downloads no weights and uses its own runtime and synthetic workspace. `RELAY_CONVERSATION_TEST_REPLY_MODE=default` selects model-default reasoning for comparison. The tests include simple output-length checks, not a complete semantic judge. Current results and remaining model-quality failures are in VERIFICATION.md.

Older unfinished checkpoints retain their original completion behavior because their files or methods may predate host provenance. They do not repeat those saves just to obtain a receipt. New requests and their subsequent restarts use the verified-save contract.

Pending text-file, reusable-skill and email-review guidance is now prepared at the end of each model attempt. It reflects current saved results, disappears after verified delivery and is never added to the durable conversation. Saving an email no longer changes the shared system prompt. This preserves a reusable prompt prefix and directs the first attempt toward the required action, without a new user step or a forced-tool protocol override. Required-question routing runs before this guidance. The existing result checks, one repair limit, source restrictions and exact reviews remain authoritative; a prompt or model response is never proof of completion.

## Data reads after tool discovery

Compact requests distinguish learning a tool’s schema from executing it. An answer immediately after metadata-only discovery is withheld while Relay requests one continuation. Repeated non-execution reports a failure. Existing operation permissions, reviewed actions and saved-result checks remain in force. Actual errors can still be explained normally.
