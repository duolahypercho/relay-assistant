# Reminders in chat

Ask “Remind me in five minutes to drink water.” The assistant can save an enabled, fixed-text reminder directly. Its chat card shows the due time and current state, with Pause/Resume and Details. Details opens the separate routines page; navigation and toggles add no chat messages and preserve the composer draft.

You can also ask “Move the water reminder to ten minutes from now,” “Pause it,” or “Cancel the water reminder.” The assistant reads the saved reminders, changes the existing entry and returns its current card. When several reminders fit, it should ask which one. A time or text edit preserves unspecified fields and an explicit pause. Rescheduling an automatically finished one-time reminder re-enables it. Editing cancels a pending delivery from the old reminder version; already delivered messages remain in the conversation.

`change_reminder` accepts an exact reminder ID, its `changeToken` from `list_routines`, and update/pause/resume/cancel. The token rejects changes based on stale state. Relative rescheduling starts at the new owner message timestamp. Changing a recurring reminder to a one-time delay should be explicit; otherwise the assistant should clarify whether to retain recurrence. Recent identical operations from the same request return the current entry without undoing a later owner change. Scheduled assistant work uses its existing routine tools; this tool cannot change its execution type or create replacement reminders. A narrow English/Chinese completion check requires a saved change before confirming direct edit requests, including after a clarification answer. A plain-text model question can become native choices only when it names two to five distinct, available reminders that were read. This fallback saves nothing.

`create_reminder` accepts either an integer delay in minutes or a one-time, daily or weekly schedule. Relative delays are anchored to the owner message timestamp, including seconds and milliseconds. Calendar schedules require an explicit IANA timezone or the saved profile timezone; the tool rejects an absent timezone instead of inventing one. Explicitly requested paused reminders remain paused. Existing `create_routine` still creates paused scheduled assistant work or reminders for review in the routines page.

The server stores the reminder atomically with its source request. Repeating the same call for that request returns the existing reminder and cannot undo a later owner pause, edit or archive. Pausing cancels queued reminder delivery; pausing an ordinary assistant routine preserves its existing accepted work. Changing a reminder's schedule or execution type in Details also updates its original chat card.

At the due time, the existing worker delivers the saved text without consulting a model. It needs the Relay server to be running; the chat app can be closed. A missed reminder catches up once after restart. Device notifications use the existing notification settings and permissions; creating a reminder grants none. This is not an operating-system alarm that can fire while the server is stopped.

A single trailing literal clause such as “Use the reminder text exactly: Water the fern.” or “提醒内容请只写：该喝水了。” is preserved from the owner request, including punctuation. A natural declaration such as `Its reminder text is "Water the fern."` also preserves the quoted payload. An unquoted declaration is recognized when a separate, supported pause sentence supplies its boundary, for example `Its reminder text is Water the fern. Start it paused so I can enable it later.` The pause instruction is excluded from the delivered text. Names, URLs and decimals are not split at arbitrary periods. Recognized quoted examples, blockquotes and code do not supply declarations. Multiple or ambiguous natural declarations, unsupported trailing clauses and escaped quoted payloads remain model-interpreted. These are narrow literal-preservation rules, not a general natural-language parser.

The same text rules apply when fixed-text reminders are created through either tool or edited through `change_reminder`. A direct creation request with one explicit name also preserves that name: it must be quoted, or end at a clock time and valid IANA zone, as in `Create a daily reminder called Water the fern at 09:00 in Asia/Shanghai.` Ambiguous or multiple names remain model-interpreted. Exact retries with the same declared name and text reuse the saved reminder even when the model changes its generated label.

Scheduled assistant work keeps its work instructions. The routine schema explains that reminder instructions are delivered verbatim, without a wrapper such as “Send a reminder message,” and that a requested name should not have the schedule appended. Actual faster-model testing exposed both mistakes. Saving a literal is independent of pause/resume authority: this parsing only preserves text and does not enable, schedule or deliver anything by itself.

For a reminder-only result, the final acknowledgement is derived from current saved state. It says scheduled, paused, cancelled, due or delivered. If the model took longer than the requested delay, it does not repeat a stale “in one minute” promise. A mixed task keeps the normal model response and its other results.

A model can set `finish: true` on `create_reminder` when that single reminder completes the request. Relay confirms directly from the saved state after all calls in the batch have run, provided no correction or missing requested deliverable remains. It saves the final checkpoint before emitting the confirmation. Failed writes, stopped work and removed results cannot publish a fast success. Selected saved methods and connected-app context retain their model continuation. Explanatory prose accompanying any tool step also prevents the fast finish, even when the model incorrectly marks its reminder call complete. This flag does not grant permissions or bypass schedule validation. It applies to this creation tool; conversational edits and scheduled assistant work retain their normal flow.

For a compound request, `finish: false` retains the model continuation and its additional answer, including across checkpoint recovery. The next model step receives the current saved reminder status outside the shared system prefix, with guidance to use that status and finish the remaining work. An early true flag cannot discard later calls in the same batch. Choosing the flag remains model judgment: host checks verify supported deliverables and provenance, not the full meaning of arbitrary requests. Omitted flags preserve the older confirmation behavior when no explanation accompanied a tool step. A purely conversational addition can still be lost if the model neither identifies it as remaining work nor provides it alongside a tool call. The acceptance scenario includes both an extra arithmetic answer and an extra saved file.

## Verification

`tests/reminders.test.mjs` covers request-relative timing, the repeated daylight-saving hour, schedule validation, timezone edits, idempotence, paused-delivery cancellation, protected assistant work, voice tool availability, truthful acknowledgements and exact fixed-text delivery after a SQLite/worker restart with no AI or browser.

Run the client journey with:

```sh
npm run build
node scripts/test-reminders-ui.mjs
# After packaging the Mac app:
node scripts/test-reminders-ui.mjs --mac
# After building Android and booting a dedicated Relay-QA-<timestamp> AVD:
# Set ANDROID_HOME and RELAY_ANDROID_TEST_SERIAL.
node scripts/test-reminders-ui.mjs --android
```

The client fixture uses a controlled HTTP model with real tools, SQLite, worker and renderer. It advances the due timestamp explicitly for deterministic delivery checks. It covers inline failure/retry, pause/resume, navigation, draft retention, edited schedules, delivery and archive states. Browser coverage includes 1365, 390 and 320 pixels, light/dark themes, English and both Chinese locales, 44-pixel controls and accessibility checks. Native Android additionally checks process relaunch. These are not live model-quality or real-time scheduling measurements.

`tests/reminder-changes.test.mjs` checks stale-state rejection, preserved fields and explicit pause, automatic reactivation, cancellation of old queued deliveries, exact new delivery text, scope restrictions, clarification and durable replay. `node scripts/test-reminder-changes.mjs` exercises conversational edits through the rendered client at desktop and phone widths; `--mac` uses the packaged Mac app, `--android` uses a dedicated Relay-QA emulator and built APK, and `--live` uses an installed local model with the same independent-cache variables as the live creation test below. Receipts are under `../relay-evidence/reminder-changes`; each receipt reports its actual scope and pass state. Only the latest reminder card in each conversation retains its live controls, avoiding repeated cards after successive edits.

`scripts/test-reminders-live.mjs` requires `RELAY_REMINDER_TEST_MODEL` and an independent `RELAY_LOCAL_MODEL_TEST_MODELS` cache. It uses actual inference on isolated port 41334, checks a three-minute reminder against the real clock across worker restart, and verifies a paused daily reminder and a Chinese recognized-text request. Recognized text does not test a microphone. The prior one-minute trial exposed a slow local-model schedule and an inaccurate relative-time acknowledgement; its evidence remains under `../relay-evidence/simple-reminders/live`. Current confirmation behavior fixes that wording, not inference latency. Very short reminders can still be late when initial model work is slow.

Creation receipts and captures live under `../relay-evidence/simple-reminders`. The aggregate `../relay-evidence/simple-reminders-verification.json` records the source tree and completed release and platform checks for that increment. Physical phones, a new iPhone-specific reminder journey, OS push delivery and signed public distribution remain separate gates.

Conversational-change captures and model diagnostics live under `../relay-evidence/reminder-changes`; `../relay-evidence/reminder-changes-verification.json` records its complete release checks when present and matching the source tree. Earlier failed attempts remain evidence, including plain-text clarification failures and the initial ambiguous recurring-to-one-time test request. A passing local-model journey does not establish accuracy or response speed for every model or phrasing.

`node --test tests/reminder-fast-finish.test.mjs` checks explicit completion, legacy/compound continuation, pending batch work, missing files, failed/removed saves, live delivery state, stop, in-flight correction, checkpoint replay and fresh status guidance. `RELAY_REMINDER_TEST_MODEL=<installed model> RELAY_LOCAL_MODEL_TEST_MODELS=<independent cache> node scripts/test-reminder-fast-finish-live.mjs` tests actual Quick inference through the browser composer on isolated port 41334. It records model calls and timings separately from saved-result assertions. It is not a physical-microphone or native-phone test.

Before reminder creation, temporary result guidance quotes the current owner request and distinguishes earlier conversation requests from pending work. It disappears after a saved result. This reduces the observed history-replay failure but is guidance, not a semantic proof that a proposed reminder matches every owner intention.
