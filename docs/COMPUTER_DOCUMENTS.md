# Documents on the private computer

Open **Computer → Files** while you have control. **Document**, **Spreadsheet**, and **Slides** create a blank document in LibreOffice. **Open** beside a supported file opens it in the appropriate desktop app. Files remain in the private computer; **Save to Relay** brings a finished file into Relay's library. The open Files list refreshes as work is saved. New office files default to the visible workspace folder. Navigation and opening documents do not add chat messages or change the unsent chat draft.

The workspace image includes LibreOffice Writer, Calc, Impress and Draw, Python's UNO bridge, `python-docx`, `pdftotext`, and Carlito/Caladea fonts. Word/Excel/PowerPoint and OpenDocument formats are supported by LibreOffice; this is not a claim of perfect format compatibility. PDFs open in Draw, and text/source files open in Mousepad without executing them. LibreOffice may retain meaningful format/import warnings. The startup tip and presentation template chooser are off by default.

You can also name a file on the computer directly in chat. The assistant's computer file reader extracts Word, Excel, PowerPoint and PDF content with the existing bounded document readers. It reads UTF-8 text in pages and identifies other binary files without passing their bytes off as readable text. The computer and Relay's library remain separate; reading a computer file does not import it or add a file card. Completed files appear in chat after export. For exact Word text changes, `computer_edit_docx` saves a new copy using the hash returned by the reader. It replaces unique literals inside an existing text run while preserving XML markup and every unrelated package part. It refuses ambiguous text, edits spanning runs, signed documents and whitespace changes that would need new formatting. Other edits use the installed document tools; the assistant must inspect the result before exporting it.

These controls appear only when the running guest advertises the installed apps. Existing computers keep their older image until the owner uses **Computer care → Check for updates → Restart & update**. That existing review closes apps and preserves saved workspace files. A new Relay app package does not silently replace a running computer. Office packages make the optional guest image larger and are downloaded during setup/update. No host office suite or administrator account is needed.

## Boundaries

The launch protocol chooses from fixed app IDs and file extensions, never shell text, URLs or operating-system file associations. File opening checks a regular file of at most 8 MB under `/workspace`, rejects traversal and symlinks through the existing descriptor walk, and uses an argument array. The server requires owner control, freezes command processes and records launches through existing durable operation IDs. A repeated confirmed request returns its receipt; a failed or uncertain launch is never repeated automatically. A launch acknowledgement is not a claim that the document rendered correctly.

Owner-launched office apps use a dedicated persistent profile so requests do not forward into an agent's frozen office process. Agent commands use their existing separate process boundary and can run LibreOffice there. For headless conversion while a GUI is open, use a different temporary profile, for example `libreoffice -env:UserInstallation=file:///tmp/office-convert --headless --convert-to pdf --outdir /workspace/results /workspace/report.docx`. Inspect exit status and the produced file. `/tmp` is cleared when the computer stops; save final outputs under `/workspace`.

LibreOffice's system configuration disables document macro execution and finalizes that setting. General Python and shell commands remain available in the isolated computer. This does not add network access, new connector permissions, credential isolation between shared guest apps, or arbitrary package installation. The guest's root filesystem stays read-only, its user stays non-root, and existing website grants and owner takeover rules still apply.

Computer document text is untrusted data. Continuation pages require the same content hash; a changed file must be read again. Cancellation stops active document parsing, and owner takeover discards an in-flight read before it reaches the model. The precise Word tool never overwrites an existing file, and writes through the existing durable computer operation protocol. Text extraction describes document content, not its visual fidelity. Precise editing and conversion still depend on the selected model and the installed document tools.

## Verified text delivery

`computer_files` can write a finished UTF-8 text file with `attach: true`. Relay performs the existing durable private-computer write, reads the actual saved file, compares its bytes with the complete requested text, and attaches that snapshot in one tool call. This avoids a separate model decision to export a simple text deliverable. Ordinary writes and the existing export/Office tools remain available. The new option does not generate Office or other binary formats.

Text larger than 256,000 characters, malformed Unicode, non-boolean attachment flags and attachment requests on non-write actions fail before mutation. Failed or changed readback produces no attachment and reports that the write already completed. Cancellation and owner takeover are checked at each asynchronous boundary. A newer owner correction skips stale delivery, preserving the completed write for correction. Exact retries bind the run, originating request and write arguments; an attachment receipt commits atomically with its file. Retrying returns the same verified snapshot, never recreates an owner-deleted attachment or replaces an owner-edited one. The existing run journal still refuses automatic replay of uncertain tool actions after a crash.

The file card counts as delivery only with the current request's host-generated receipt and unchanged actual file fingerprint. Matching saved bytes proves persistence and delivery, not that the model understood every requested detail.

## Verification

`npm run computer:office:test:ui` and `npm run computer:office:test:mac` use actual Docker desktops and original synthetic DOCX, XLSX, PPTX, PDF and text files. They check opening every supported app family, Unicode editing and saved bytes, new-document creation, agent-side PDF conversion, command freezing, the runtime's locked macro setting, rejected paths, durable launch retries, saved files after stop/start, responsive controls, scoped accessibility and untouched chat history/drafts.

`npm run computer:office:test:ios` uses a disposable iPhone Simulator, the production bundled app, a private authenticated HTTPS fixture and real LibreOffice. It opens a file, types through the native keyboard, creates slides, and checks navigation and complete app relaunch. No owner account, model credentials or conversation are used. Android web assets are synchronized; native Android execution and physical-device verification remain separate release gates.

`npm run computer:office:test:live` and `npm run computer:office:test:live-mac` use explicitly selected dedicated model weights and a test Docker engine. The live model receives a plain request to update an original Word fixture and attach Word/PDF copies. The harness checks actual exported content, an unchanged original, retained table/bold/footer content, separate-page preview with draft preservation, and honest handling of a malformed source. A completed chat response alone does not pass. Set `RELAY_COMPUTER_TEST_MODEL`, `RELAY_LOCAL_MODEL_TEST_MODELS`, and `RELAY_COMPUTER_TEST_DOCKER_HOST`; model serving uses a separate port and temporary workspace. Failed attempts remain in evidence and are not counted as passing acceptance.

Evidence is under `../relay-evidence/computer-office/`; the final aggregate is `../relay-evidence/computer-office-verification.json`. This work adds a bundled document suite, not a managed app marketplace or general runtime upgrade service.
